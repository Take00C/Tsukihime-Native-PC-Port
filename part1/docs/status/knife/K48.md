# K48: the launcher and updater on macOS and Linux

Package K48 began on 2026-11-03 on Kimi's branch `kimi/launcher-unix`; the round-5 review fixes followed on 2026-11-04. It was integrated into the owner's repository as `f87fdd2` from `kimi/launcher-unix` at `bb1f1d7`; the branch's own commits are not in this history. It shipped in **v0.1.7** after the review rounds of section 7, which supersede the numbers in section 4. No game data or TYPE-MOON art was added, nothing was pushed, and no release archive was produced for upload.

This report replaces the intermediate K48 verification, including its unreliable headless-test results.

## 1. Launcher behavior and appearance

- The Unix launcher uses Avalonia 11.3.22 and is named `TsukihimeLauncher` on Linux x64, macOS arm64 and macOS x64. Windows keeps its WPF launcher and Windows update asset. `src/Tsuki.Linux.slnx` includes the Unix launcher and tests; the Windows solution keeps its existing projects.
- The seven pages use a forced dark variant and the Windows night-blue palette, serif headings, gold accents, crescent sidebar, runtime hero art, card layout, and explicit hover, pressed, focused, disabled, drop-down and dialog styling. The Help icon is a text `i`, not an unavailable icon-font glyph. Footer content is centered and ready-row Fix buttons have their own aligned column.
- `[CallerMemberName]` notifications are restored. Update status, visible update errors, the update button, and PLAY state refresh. Toasts display for six seconds. External game processes disable PLAY and refuse an update before downloading. Restore asks first; a declined restore writes nothing.
- The platform-neutral launcher files are linked rather than forked. `LauncherFolderChoice` is shared by WPF and Avalonia: a wrong folder never replaces the remembered one. `AppSettings` and `ProfileDirectory` preserve profile locations and settings meanings. Explicit `--data` and `--game` paths survive a restart.
- Runtime hero art is decoded from the player's own files into memory only. No art is packaged. Linux can create a quoted `.desktop` entry; macOS does not create shortcuts.
- Steam Deck instructions point Steam at the `Tsukihime` game, preserving Game Mode fullscreen defaults and Launch Options. The launcher is documented separately for Desktop Mode backups, folder selection and updates. Existing Linux v0.1.6 users make their first update manually because that version has no launcher.

## 2. Updater and release safety

| area | final behavior |
|---|---|
| Assets and checksums | Windows keeps `Tsukihime-vX.Y.Z-win-x64.zip`; Linux uses the Linux tar.gz and each Mac architecture selects only its own ZIP. One `SHA256SUMS.txt` can list all four. Personal builds never update. A bad checksum changes no installed file. |
| Linux archives | Checked extraction refuses absolute, backslash, drive-colon, dot-segment, control-character and duplicate names, links and special entries, special permission bits, excessive per-file and total uncompressed sizes, missing programs/assemblies, mismatched or personal builds, and non-executable hosts. Updates preserve the profile and roll back failed apply/restart attempts. |
| Mac archives | Metadata other than ditto's `__MACOSX/` signature entries, unsafe names, files outside `Tsukihime.app`, duplicates, links, special files/modes, wrong architectures, signatures, entry points, bundle CodeResources and executable modes are refused. Main launcher signatures use `io.github.take00c.tsukihime`; the nested game host uses `io.github.take00c.tsukihime.Tsukihime`, which `codesign --deep --prefix io.github.take00c.tsukihime.` gives it (§6). |
| Bundle replacement | `renameatx_np` uses its real five-argument declaration and macOS `AT_FDCWD = -2`. The update stages in the hidden `.Tsukihime.app.update` beside the bundle, marked by `TSUKIHIME_UPDATE.txt`; an unmarked folder of that name is never deleted and stops the update, and a marked one that cannot be emptied stops it before the working bundle is touched. Injected-exchange success and rollback tests cover the state transitions; the real syscall remains a Mac check. |
| Native dependencies | Linux requires `libSkiaSharp.so` and `libHarfBuzzSharp.so`. Mac additionally requires `libAvaloniaNative.dylib`, `libSkiaSharp.dylib` and `libHarfBuzzSharp.dylib`. ELF/Mach-O type, architecture, minimum OS and relocatable IDs/dependencies are checked. Universal launcher dylibs are validated per selected slice; apphosts remain thin. Official `@rpath` IDs are accepted for Avalonia/SDL, not for FFmpeg. |
| Avalonia packaging | The real `/usr/local/lib/libAvalonia.Native.OSX.dylib` ID is normalized to `@rpath/libAvaloniaNative.dylib` before signing, in both universal slices. The fixed-length rewrite preserves every following byte. |
| CLI separation | The launcher links shared release rules and icon checks instead of referencing `Tsuki.Cli`. `Tsuki.Cli`, its apphost/runtime files and `Tsuki.DevBridge` do not ship in the Unix launcher publish. |
| Remaining guards | Archive caps also apply in `release-sums`. Both apphosts and required libraries require platform 1 and a suitable deployment version. Bad plists get no success note. On macOS only, SDL fullscreen events synchronize requested state (the green button). |

## 3. CI, packaging and documentation

- `macos-release.yml` has corrected smoke commands and a clean `ditto` extraction followed by `codesign --verify --deep --strict`. The Windows Avalonia test job uses the same no-FFmpeg build options as the other Windows jobs. A local `actionlint` run passed both workflows.
- `package_linux.py` and `package_macos.py` require the launcher native libraries as well as the player programs and libraries. Python/C# ICNS byte agreement is tested by executing the actual Python writer and comparing its bytes with C#.
- Linux dependency inspection confirmed the apphost/SDL requirements and additional Skia requirements: `libfontconfig.so.1`, `libfreetype.so.6`, and their Expat, zlib, bzip2, PNG and Brotli dependencies. This WSL image has no FFmpeg 9 libraries, so FFmpeg `ldd` evidence remains outstanding.
- The Windows publish still has **283 files** and no Avalonia, CLI or dev-bridge additions. The Linux publish has no `Tsuki.Cli` or `Tsuki.DevBridge` files.
- All seven pages were rendered and inspected without game art. These images and the other verification files are not committed.

## 5. Not verified

1. A real macOS update, `renameatx_np` exchange, restart and rollback on either architecture.
2. Real ad-hoc signing, `ditto` ZIP output, signature verification of that output, Gatekeeper and quarantine behavior. The structural apps are unsigned and must not be uploaded.
3. Actual macOS OpenGL, desktop file pickers, native hero art, audio, trackpad/green-button behavior, sleep/resume and Dock behavior, including whether the game produces a second Dock icon.
4. SteamOS, Game Mode, Steam Input, gamescope and physical Steam Deck behavior. Documented dependencies do not establish SteamOS compatibility.
5. Hosted GitHub Actions and uploaded artifacts. Local lint does not prove a hosted run.
6. Real Mac FFmpeg compilation, decoder behavior and `ldd` inspection. Structural FFmpeg fixtures are not compiled libraries.
7. Retail-game desktop rendering, audio and gameplay in this round. No game data was used for these verification runs.
8. The Avalonia launcher on a real Linux desktop: the X11 or Wayland folder picker, fonts and fontconfig on SteamOS, and the `.desktop` entry. Every Linux launcher run was headless in WSL.
9. Whether real `ditto` ZIPs carry the signature attributes of the non-Mach-O files in `Contents/MacOS` as `__MACOSX/` entries. The packager now zips with `--sequesterRsrc`, and the workflow summary records the attribute and entry counts.

Before release, run the manual Mac workflow, inspect both signed apps and real `ditto` ZIPs, test update/restart on Mac hardware, and run `release-sums` once with all four real assets. Test desktop launchers and Deck hardware with the player's own files. Keep the Windows asset name unchanged; the release itself sets the new version.

## 7. v0.1.7 (2026-11-06)

Three review rounds (a heavy review, a Steam Deck review and a macOS review, then a final review of the merged branch) were fixed and merged. What changed after round 5:

- **Updater policy.** The Linux and Mac updaters check a small policy: safe names, plain files, safe modes, limits, forbidden files, the personal mark, both programs with their runtime files, every file the new `deps.json` lists, versions, architecture and, on a Mac, `codesign --verify`. They no longer freeze this release's file list, so a later release with other licences, sonames or helpers still installs. `release-check` and `release-sums` keep the full lists. A refusal shows one sentence; `launcher.log` lists every reason.
- **Mac.** Signing uses `--prefix io.github.take00c.tsukihime.` (section 6). The update refuses a drive that cannot swap the bundle before downloading, honours Cancel while unpacking, and keeps the installed app when the swap fails. The launcher shows Arcueid in the Dock, names Mac keys and the LGPL 2.1+ FFmpeg, and has its own app menu. macOS `._` and `.DS_Store` files are ignored.
- **Linux and the Deck.** The application-menu entry starts the game with the face icon. The launcher's Fullscreen switch writes `display_mode`; a Deck PLAY passes no window flag. The window fits a Deck's desktop. PLAY comes back, and the profile is read again, after a game the launcher did not start.
- **The game on Linux and macOS.** One game per profile across sessions (`game.lock`); the first SIGTERM is a saved quit; every start writes `last_run.log`, best effort; `~` works in path options; a bad command line goes to `crash.log` and a box. The run log records Steam, SDL, window, pad, audio-device and vsync facts. Windows is unchanged: the final review found the same file list (plus `docs/MACOS.md`), logs, profile files and launcher self-tests as v0.1.6.
- **CI.** The Mac workflow checks the version first, runs the real updater on the real ZIP after the uploads, re-checks on macOS 26, keeps diagnostics after a failure and has informational window smokes. Push CI runs the real Linux update test.
