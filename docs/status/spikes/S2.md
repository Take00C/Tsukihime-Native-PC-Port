# Spike S2: movie A/V sync (`prologue_en.mp4`, FFmpeg.AutoGen + SDL3 + GL 3.3)

**Verdict: PASS.** Movie id 46 (`image/movie/prologue_en.mp4`) plays in a 1920 x 1080 SDL3 / GL
3.3 core window. FFmpeg.AutoGen demuxes and decodes on the movie threads, the planes go through
the PS #4 YCbCr shader, and the audio clock is the master. The thresholds are those of the
ROADMAP M0 spike table:

Over all 2,620 ticks of the last 43.7 s, the clock never left the shown frame's display interval by more than 0.53 ms (0.000 ms with the first design). | PASS |
| dropped frames at 60 Hz | 0 | **0 dropped, 0 late.** Covered: 1,349 frames from 0 s plus 1,309 frames from 345 s to the end (`final_sw_from0`, `final_sw_end`). 21 of the 23 windowed runs had 0 drops. In the other 2, one ~40 ms stall inside `SDL_GL_SwapWindow` dropped 1 frame each (section 8). In those 2 runs the decoder still had 5..7 frames ready. | PASS (see 8) |
| decode < 1 core | < 1.0 core | while playing: **0.15..0.25 cores** for all movie threads in software (16 frame threads), 0.043 cores with d3d11va. Headless over the whole file: software needs 0.210 cores at 30 fps (6.99 ms CPU per frame), or 0.164 cores with 1 thread. | PASS |

The fallback (Media Foundation behind `IMovieDecoder`) is not needed. The spike found three

- hardware decode works with copy-back, but it gains nothing that is needed;
- a swap stall of about 40 ms under heavy machine load drops one frame.

| `Queues.cs` | `VideoFrame` (pinned Y / U / V or Y / CbCr), `FrameQueue` (pool + ready queue), `PacketQueue`, `PcmRing` (lock-free SPSC float ring, 4 s) |
| `AudioOut.cs` | `SDL_OpenAudioDeviceStream` with an `[UnmanagedCallersOnly]` get-callback that pulls exactly the requested frames from the ring (the future mixer's pull model, ARCHITECTURE 7.1). **Audio clock** = media frames handed to SDL before the last callback, plus the time since that callback, minus one device buffer (480 frames = 10 ms). The extrapolation is clamped to one chunk until the stream has drained, and the clock never runs backwards. |
| `YuvRenderer.cs` | Three R8 textures (yuv420p) or R8 + RG8 (NV12). Upload with `glTexSubImage2D` from pinned memory, or through a PBO ring. Full-screen-triangle draw, 16:9 letterbox. The PS #4 fragment shader uses the float32 bit patterns of `tsuki.compose.ps_ycbcr`, operation for operation (`uintBitsToFloat(0x3F950B0Fu)` ...). `GL_TIME_ELAPSED` queries time the upload and the draw. 1920 x 1080 offscreen read-back. The same fragment source is also compiled as GLSL ES 3.00. |
| `Player.cs` | SDL3 window (1920 x 1080 pixels) with a GL 3.3 core context, vsync (swap interval 1) at the monitor rate (144 Hz; ARCHITECTURE 6.2 default). **60 Hz logic ticks** from an accumulator pick the newest frame with `pts <= clock`. Optional tick-phase alignment and cadence lock. Statistics: offsets, cadence histograms, drops, late frames, per-thread CPU, timer queries; CSV logs per tick and per present. |
| `Bench.cs` | Headless decode of the whole file as fast as possible (demux + decode + plane copy); AAC decode of the whole track |
| `Native.cs` | `GetCurrentThreadId`, `GetThreadTimes` and `GetSystemTimes` (kernel32), for per-thread and machine-wide CPU |
| `Stats.cs` | Nearest-rank percentiles and the JSON writer |
| `compare_frame.py` | YCbCr check: our planes vs the ffmpeg CLI, our GL read-back vs `tsuki.compose.ps_ycbcr` (GL-style bilinear chroma) and vs swscale |

Definitions used below:

- **offset** = pts of the frame selected at a tick minus the audio clock at that tick. A frame
  is shown while the clock is in [pts, pts + 33.3 ms), so values from 0 to -33.3 ms are in
  sync.
- **sync error** = how far the clock is outside the shown frame's interval (0 = correct
  frame).
- **dropped** = a source frame that no tick ever selected.
- **late** = a tick wanted a frame that was not decoded yet (the ready queue was empty).
- **never presented** = a frame selected by a tick but replaced before any swap showed it.

## 6. Upload path

- Direct `glTexSubImage2D` from pinned managed arrays: 0.38 ms CPU / 0.02 ms GPU per frame.
- A PBO ring: 0.35 ms CPU.

At 30 uploads per second either costs about 1.1 % of one core on the main thread. Direct upload
is enough; PBOs are not needed for movies.

## 7. Frame cadence: when the 60 Hz tick reads the clock

**First design (`--tick-clock now`).** The tick ran when the 144 Hz present loop reached it, so
it sampled the audio clock 0..7 ms after its nominal grid time. The lag moves in a 5-tick
pattern, because 144 / 60 = 2.4. When a frame boundary fell inside that window, the cadence
became 1-3 ticks instead of 2-2: judder, though no frame was dropped. Measured frames with 1 or 3 ticks
(the first frame, which waits for the audio start, included):

- `play_sw_from295`: 89 of 299;
- `play_sw_pbo`: 27 of 899;
- `readback_sw`: 13 of 779;
- `play_d3d11va_direct`: 5 of 1,349;
- 1..3 in the other runs.

So it depends on the random start phase.

**Nominal tick clock (`--tick-clock nominal`).** The tick reads the clock at its grid time
(`nextTick`), which leaves only the clock's own jitter (about +-0.6 ms). Near a boundary the
cadence still flips:

| run | tick phase | cadence lock | ticks per frame | sync error max |
|---|---|---|---|---|
| `cad_nominal` | natural | off | {1: 9, 2: 881, 3: 8, 4: 1} | 0 |
| `cad_nominal_phm06` | -0.6 ms (the grid crosses the frame boundaries during the run) | off | {1: 26, 2: 847, 3: 26} | 0 |
| `cad_nominal_phm06_lock4` | -0.6 ms | 4 ms | **{2: 899}** | 0.62 ms |
| `final_sw_from0` | natural | 4 ms | {2: 1,348} + first frame | 1.10 ms |
| `final_sw_end` | natural | 4 ms | {2: 1,308} + first frame | 0.53 ms |

**Cadence lock (4 ms).**

- A frame that has had only 1 tick keeps a second tick when the next frame became due less
  than 4 ms ago (this "hold" never triggered in these runs).
- A frame that has had 2 ticks gives way up to 4 ms early.

It removes the judder completely, and the clock stays within 1.1 ms of the shown frame's
interval. The 50 ppm clock drift moves the phase by 19 ms over the movie, more than one tick, so
without the lock every full playback would cross a boundary at least once.

## 8. Presentation stalls under load

In 2 of the 23 windowed runs (`cadence_phase0_lock4` and `cadence_phase8_nolock`, both at about
21:15-21:16 UTC), `SDL_GL_SwapWindow` blocked for 20..38 ms. This happened 7..9 times per 30 s,
roughly every 2..3 s. The CPU work in those iterations was 0.003..0.9 ms. One stall of about
40 ms skipped one source frame in each run. The catch-up ticks then ran at the same clock
value, and the decoder had 5..7 frames ready.

Presents over 16.7 ms without a drop also occurred in 3 other runs: `play_sw_end` (3, max
22.9 ms), `play_d3d11va_direct` (1, 20.9 ms) and `play_d3d11va_t0` (2, max 24.4 ms). In each
read-back run the one long present is the read-back itself (42.2 / 22.4 ms). Other agents' jobs
were running throughout: 6..7 cores busy at 21:15, many dotnet processes, Python jobs, and
S4.BigPicture runs (GPU uploads; processes seen at 21:17, 21:18, 21:19 and 21:21 UTC). The cause
was not identified. No stall was seen in the 7 runs from 21:19 to 21:24 UTC, although
S4.BigPicture was running then.

This is not a decode or sync problem. It is the presentation-side risk that ARCHITECTURE 6.2
and R4 cover. A swap stall over one movie frame (33 ms) drops a frame in any player. The
acceptance re-run should be on an idle machine.

## 9. Recommendations for M2 (stream E movie thread)

1. Keep the threading of this spike:
   - demux + AAC on one thread;
   - H.264 on another, with FFmpeg frame threads (`thread_count` 0) and 8 pinned frame
     buffers;
   - AAC float stereo 48 kHz into the mixer ring;
   - frame selection on the main thread.
2. Audio clock: the media frames rendered by the mixer callback, plus the time since the
   callback, minus one device buffer. Clamp the extrapolation to one period until the stream
   drains; after that use the frame clock, as ARCHITECTURE 7.5 says for silent tracks.
3. The 60 Hz logic step reads the clock at its nominal tick time, not when the present loop
   reaches it, and applies a cadence lock of about 4 ms (section 7). Both are deterministic
   and testable without a GPU (feed a synthetic clock).
4. Software decode by default; d3d11va (auto threads) is optional. Do not use d3d12va with
   `thread_count` 1.
5. Upload directly with `glTexSubImage2D` (yuv420p as 3 R8 textures). The PS4's NV12 path is
   the same shader with an RG8 chroma texture; both were verified.
6. Movie end ("movie ended" releases `_TOMW`): video EOF, empty queue, and the clock past the
   last pts + 1/fps. The event came 19..28 ms after the last frame was first presented.

## 10. Open issues

- The windows were limited to 45 s by the spike rule, so the movie was played in segments:
  0-45 s, 55-65 s, 295-305 s and 345 s to the end. The whole file was decoded headless
  (11,660 frames). A full 388.7 s windowed run is left for the M2 slice test (RR 7.5).
- The machine was not idle during the measurements (section 8). L should re-run
  `final_sw_from0` and `final_sw_end` on a quiet machine.
- Not tested: a 60 Hz display mode (the monitor is 144 Hz, and changing it is a system
  setting); acoustic output latency (the clock assumes one 10 ms device buffer; any further
  WASAPI / driver latency is a constant offset we cannot see without a loopback capture);
  zero-copy D3D11-GL interop.
- `compare_frame.py` is a Python file under `src/Spikes/S2.MovieSync/`. If the pre-commit
  allow-list does not accept it there, it can move to `tools/` with the lead's agreement.
