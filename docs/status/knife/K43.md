## 2. How it works

| step | code | rule |
|---|---|---|
| when | `LauncherModel.LoadGameIconAsync` -> `StampIconsAsync` (`LauncherModel.ProgramIcons.cs`) | after every refresh of the game folder (window start, a chosen folder, Recheck, the end of a game, the restart after an update: the update brings the crescent back with its files), and when the switch changes. Only with `StampProgramIcons` set: the window (`LauncherApp`) and `--stamp-selftest`; `--render`, `--selftest` and `--update-selftest` never change their folder. One stamp at a time (a semaphore); the latest setting and icon are read when it runs. Not in a personal build (logged once); not while an update is downloading or installing (`UpdateBusy`) |
| what | `LauncherModel.Stamp` | switch on: her icon from the profile (`IcoFile.ReadFile` of `GameIconPath`; nothing is written while there is none: no ready folder, no picture); switch off: the crescent from the launcher's own resource `Assets/tsukihime.ico` (= `assets/icon/tsukihime.ico`) |
| clean-up | `ExeIconStamp.CleanLeftovers` (the repair before every stamp and at the window's exit, the deletion at the first stamp of a session: review, section 7) | a program that is missing gets back its newest `.icon-old` copy that reads as a program, else its checked `.icon-new` when that is a plain apphost (a stamp cut off between its two renames); nothing of a missing program is deleted; then every `<program>.icon-old`, `<program>.N.icon-old` and `<program>.icon-new` is deleted (a copy still in use stays: the launcher that ran the last stamp). Other names (`notes.icon-old`, the updater's `.old`) are never touched |
| the folder | `ExeIconStamp.StampFolder` | skipped whole when `update-staging\` exists (an unfinished update) or, if anything needs writing, when `UpdateInstaller.ProbeWritable` fails (Program Files); a start whose programs already carry the icon writes nothing, not even the probe |
| one program | `ExeIconStamp.StampExe` | skipped: already the wanted images (`IcoFile.SameImages`: the same images, byte for byte, in order; `Unchanged`), not there, read-only, the game of this folder running (`GameLauncher.IsGameRunningFrom`; the next refresh, after the game ends, does it), not a plain apphost (`ApphostProblem`: not a PE program, a managed assembly, over 16 MB, signed, data after the last section, no bundle marker or a single-file bundle (the 8 bytes before the marker not 0, as `HostWriter.IsBundle` reads them), the `.dll` not beside it, the resource section not the last section), no single group 32512 |
| the copy | `WriteCopy`, `UpdateIcon` | `File.Copy` to `<name>.icon-new`; `BeginUpdateResourceW(copy, FALSE)`; every RT_ICON the old group 32512 names is deleted **in each language it has** (read with `PeIcons.ResourceList`, not assumed; the builds have language 0); the new images become RT_ICON ids that no other group uses (1..n here); RT_GROUP_ICON 32512 is replaced in the group's own language with a GRPICONDIR built from the .ico's directory entries (`IcoFile.GroupDirectory`: the 12 bytes of each entry as the file has them, the RT_ICON id instead of the offset, as the C# compiler writes it); `EndUpdateResourceW` (discard on any failure). A sharing violation (a scanner on the new file) is tried again, three times in all |
| the check | `ExeIconStamp.Verify` | before anything is replaced: the size within (old - old images - 64 KB, old + new images + 64 KB); still a plain apphost (bundle marker with offset 0, no signature, no overlay, `.rsrc` last); the headers (machine, characteristics, entry point, image base, alignments, subsystem, DLL characteristics, stack and heap, every data directory but the resources) identical; every other section identical (name, address, sizes, SHA-256 of its bytes); the group reads back (`PeIcons.IconGroup`) as exactly the wanted images; one group 32512, in the old language; no RT_ICON left without a group; every other resource (RT_VERSION, RT_MANIFEST) the same list and the same bytes |
| the swap | `ExeIconStamp.Swap` | under `SwapGate` (PLAY takes the same lock around its `Process.Start`), refused when `update-staging\` appeared meanwhile. Since the review (section 7): `Tsukihime.exe` is replaced in one step (`File.Move(copy, exe, overwrite: true)`); `TsukihimeLauncher.exe`, which runs, is renamed to `<name>.icon-old` (or `<name>.2.icon-old` when that one is still in use: two stamps in one session) and the copy moved in; when the move fails, the original is moved back, else the checked copy moved in after all (five tries, about a second), and only if neither can be moved are both kept and the log says `MISSING`. Then the `.icon-old` is deleted (the running launcher's image cannot be: the next start does it), `SHChangeNotify` for that path, and the program is read back once more |

`TsukihimeLauncher.exe` is the running process: renaming a running program works on Windows (the updater relies on it, `UpdateInstaller.Apply`), so the
launcher stamps itself and its old image waits as `TsukihimeLauncher.exe.icon-old` until the next start.

### What it must not break (checked)

| thing | why it holds |
|---|---|
| the updater (`UpdateInstaller`) | the stamp's names are `.icon-new` / `.icon-old`, never `.old`; the updater's journal, rollback and clean-up only touch the `.old` files the journal names and the staging folder; the stamp skips a folder with `update-staging\` and does not start while an update is busy; the update replaces the stamped programs like any other file (`TheStampedProgramsStillStart...` and the update tests ran in the same suite) |

| the staged-release check (`UpdateInstaller.Check`) | reads the staged `TsukihimeLauncher.dll` marks and version, not the programs' icons |
| the game's own window icon | the class icon is group 32512 of the running program (`GameWindow.ExecutableHasApplicationIcon`); it is still there (now her face), and the run-time Arcueid icon is set on the window as before |
| the desktop shortcut | `Tsukihime.lnk` still points at `Tsukihime.exe` with the profile's `.ico` (unchanged code) |

## 5. For the lead: the self-test on a copy of a release folder

The self-test exists from this tree on (v0.1.4 and older releases do not have it). It changes the programs of the folder it runs from, so it runs on a copy,
with a profile of its own (it refuses to run without `--data`); the game folder is only read.

```
# a release folder of this tree (artifacts/wf_stamp_pub/out is one, made as below; never -p:TsukiPersonalIcon, never artifacts/dist)
dotnet publish src/Tsuki.Launcher -c Release -r win-x64 --self-contained -p:DebugType=none --artifacts-path artifacts/wf_stamp_pub -o artifacts/wf_stamp_pub/out
dotnet run --project src/Tsuki.Cli -c Release -- release-check artifacts/wf_stamp_pub/out           # "may be released" (crescent)

# PowerShell: a copy, a temporary profile, the real game folder (read only); no window, no sound
$t = Join-Path $env:TEMP 'k43-check'; New-Item -ItemType Directory -Force $t | Out-Null
Copy-Item -Recurse artifacts\wf_stamp_pub\out (Join-Path $t 'Tsukihime')
$env:SDL_AUDIO_DRIVER = 'dummy'
$p = Start-Process (Join-Path $t 'Tsukihime\TsukihimeLauncher.exe') -ArgumentList '--stamp-selftest', (Join-Path $t 'on.txt'), '--data', (Join-Path $t 'profile'), '--game', $env:TSUKI_GAME_DIR -Wait -PassThru
$p.ExitCode; Get-Content (Join-Path $t 'on.txt')                                                     # 0, no FAIL line; "after: ... Arcueid (7 images)"
dotnet run --project src/Tsuki.Cli -c Release -- release-check (Join-Path $t 'Tsukihime') --dump (Join-Path $t 'dump')   # REFUSED: a stamped install is not a release
$p = Start-Process (Join-Path $t 'Tsukihime\TsukihimeLauncher.exe') -ArgumentList '--stamp-selftest', (Join-Path $t 'off.txt'), '--data', (Join-Path $t 'profile'), '--game', $env:TSUKI_GAME_DIR, '--stamp-off' -Wait -PassThru
$p.ExitCode; Get-Content (Join-Path $t 'off.txt')                                                    # 0, no FAIL; "after: ... the port's crescent (10 images)"
dotnet run --project src/Tsuki.Cli -c Release -- release-check (Join-Path $t 'Tsukihime')            # may be released again
```

`<file>.launcher.txt` beside each report is the stamped launcher's own `--selftest`. Without `--game` (and without `TSUKI_GAME_DIR`) the Arcueid run has no icon to
write and says `FAIL the Arcueid icon was built ... none`; `--stamp-off` needs no game folder.

## 6. Open issues

1. **One crash in 41 self-test runs of the publish copy, not reproduced.** The second run on the publish copy (`--stamp-off`, the profile of the first run)
   ended with `0xC0000005` in `coreclr.dll` (WER APPCRASH, `TsukihimeLauncher.exe` 0.1.4.0, offset `0x3590bf`), after the self-test had written `arcueid_icon=off`
   and before the stamp's clean-up ran: nothing in the folder changed (both programs still Arcueid, the earlier `.icon-old` still there, no `.icon-new`), no
   report was written. The same command on a fresh profile passed, and so did 38 further alternating runs on the reused profile. In that window the launcher
   runs its folder refresh (the game folder check, the banner art, monitors, controllers: code this package did not change) and none of the stamp's Windows
   calls; the WER report itself cannot be read without administrator rights. Worth watching in the window mode's `launcher_crash.log` / WER; the stamp's
   safety did hold (a crash at any point leaves either the original or a checked copy). Correction (review, section 7): "the next start repairs a cut-off swap"
   holds for `Tsukihime.exe` only; a launcher cut off between its own two renames cannot start to repair itself, see section 7.
2. **(Fixed in the review, section 7.) The update's apply does not wait for a running stamp.** `RunUpdateAsync` (K40/K42's file) checks the game, downloads, then calls `UpdateInstaller.Apply`;
   a stamp started just before "Update now" finishes in about a second, long before a 100+ MB download, and a stamp never starts while `UpdateBusy`. To make
   it airtight, `RunUpdateAsync` could `await ProgramIconsIdle` before `Apply` (one line, in the other package's file: not changed here).
3. **The game started from Explorer in the instant of a swap.** PLAY is guarded by `SwapGate`; a double-click on `Tsukihime.exe` (or its shortcut) in the
   microseconds between the two renames would get "file not found", and a game started from Explorer after the running check but before the swap keeps
   running from its renamed image (deleted at a later start). Both are harmless and very unlikely.
4. **Explorer's icon cache** may show the old picture until it refreshes (the user accepted this); only the one file is announced, no cache is flushed.
5. **Antivirus**: a program that rewrites executables can draw a scanner's attention (the user accepted this). The copy is written with the documented
   resource API, checked, and only then moved in; a scanner holding the new copy just makes the stamp try again and then give up (logged).
6. (Fixed in the review, section 7.) `release-check` names a stamped folder "a personal build" in its REFUSED line (its wording is K28's, `src/Tsuki.Cli/Commands/ReleaseCheckCommand.cs`, not
   changed here); `PUBLISHING.md` 1.4 says to read it as "or an install the launcher stamped".
7. The visible window was not opened (rules): the stamp in the window mode is the same `StampIconsAsync` the self-test drives, started from the same
   `LoadGameIconAsync`; the switch was drawn by `--render`, not clicked.
8. The user's note on this task (2026-11-01): *"the old release files had the arecuid face not the crescent ... don't do that again"*. The release publishes
   of this project were checked by `release-check` and carried the crescent (K41 section 4: "4 ok lines each (crescent icons ...)"); what showed her face
   were the personal build in `artifacts/dist/Tsukihime` (compiled in, package K28) and, in every build, the window, taskbar and shortcuts (package K23). With
   this package an installed release shows her face on the programs too, after the launcher's first start, while the zip itself stays free of her art. Putting
   her face into the release zip itself would ship TYPE-MOON's art in a public download; that was not done and is the user's and the lead's call.
