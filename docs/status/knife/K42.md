# K42: the update button is always there (GitHub issue #6, "Something around this corner")

Package K42 (label `k42`), run on 2026-11-01 in the main working tree `D:/TsukihimePort` on `4815062` (v0.1.4), beside the package that stamps Arcueid's face
into the installed programs at run time (another agent, same tree, same day; its files are not part of this one). Nothing is committed. Builds in
`artifacts/wf_btn` (Debug, `-warnaserror`, 0 warnings); the renders ran from a copy of the build output in a temporary folder with a temporary `--data`
profile. **No network call to GitHub**: every check went to the loopback stand-in (`FakeGitHub`) on 127.0.0.1 or to a closed loopback port, and the render
draws made-up results. Every launcher run was a verification mode (`--render`, `--update-selftest`, the restarted launcher's `--selftest`): no window. The
game folder (read only, for the render's art), `%APPDATA%\Tsuki`, `artifacts/dist`, `-public`, `-release` and `-upload*` were not written. No PowerShell with
Add-Type, DllImport, P/Invoke, LoadLibrary, base64 or Invoke-Expression.

Issue #6 asked again for an update button "around this corner" (the cursor was in the footer, just left of **Log**). K40's button was only shown once a newer
release had been found, so a player who was up to date (or offline at the start) never saw it. The user chose: **always visible**.

## 1. What the player sees

| state | the footer button (left of **Log**, 42 px high like Log) | a press |
|---|---|---|
| idle, up to date, offline at the start | **Check for updates**: Log's glass with a muted sync glyph (`CheckUpdatesButton`), at least as wide as that text | a manual check, the same as Help & about > **Check now** |
| a check runs (the start's or a manual one) | **Checking…** (U+2026), dimmed, cannot be pressed; same width, so the footer does not jump | - |
| a newer release is known | K40's gold **Update to vX.Y.Z** with the download glyph and dot (`UpdateButton`, unchanged) | starts the update at once (one click, section 7): K40's overlay opens on the download |
| an update downloads or installs | **Update to vX.Y.Z**, disabled (the overlay is up anyway) | - |
| a personal build (package K28) | **Check for updates**, quiet, can be pressed | the toast *This personal build doesn't update itself. New versions are on the port's GitHub Releases page.*; no check, one line in launcher.log |

After a **manual** check (the footer button or Check now) the footer's toast says the outcome: *You have the newest version (v0.1.4).*; offline or any error
(no connection, a 404, an answer that is no release list, GitHub's hourly limit): *Couldn't reach GitHub. Try again later; Help & about says what went wrong.*
(the Help page's status line has the exact reason, as in K40). A manual check that finds a newer release opens the overlay at once (unless the yes / no
question is up). The start's check (setting `update_check`) stays silent, as before: the button just turns gold when it found something.

Tooltips follow the state ("Ask GitHub whether a newer release of the port is out", "Asking GitHub for the newest release", "v0.1.5 of the port is on GitHub:
see what is new and install it", "This personal build doesn't update itself"); `AutomationProperties.Name` is the label, `HelpText` the tooltip. Keyboard: the
button is in the tab order before Log; when it is disabled by its own check while it has the keyboard, it takes the keyboard back once it can be pressed
again; when the update overlay closes (Later / Close), the keyboard goes back to the footer button. The status line on the left now trims with "..." (it sat
in a horizontal StackPanel, which never trims; now a DockPanel), so the button never squeezes Log or PLAY (PLAY keeps its 188 px).

## 5. Open issues

1. The visible window was not opened (verification modes only): the hover look, a real mouse click, the tooltip and the keyboard returning to the button
   are code-read and seen in the renders (the focus rim in `update_toast_personal.png`), not clicked.
2. **Check now** on the Help page is the same manual check, so it now also shows the toast and opens the overlay when it finds a release (deliberate: one
   manual check). The start's check is unchanged and silent.
3. While the start's check runs (normally well under a second, at most the 15 s timeout when GitHub does not answer) the button reads "Checking…" and cannot
   be pressed.
4. All check errors share one toast; the Help page's status line and launcher.log have the exact reason (rate limit, 404, no connection).
5. At the window's smallest width (960 px) the Play page's Quick settings clip some segment labels ("Keyboar", "PlayStat" in `update_footer_narrow.png`); that
   is the page above the footer, unchanged by this package.
6. As K40 / K41: not tried against the real GitHub.

## 6. Review (2026-11-01, the same day)

Three reviewers read the uncommitted tree together with package K43 (the program icons); the fixer checked each finding against the code. Findings that
touch this package's files (K43.md section 7 has the rest):

| finding (severity) | checked | done |
|---|---|---|
| pressing the always-visible button twice within 6 s made the second toast vanish about a second later: each `ShowToast` started its own timer, and the first one cleared the same text (minor) | real (`LauncherModel.ShowToast`, older than K42 but now the button's only feedback) | each call takes a number (`_toastShown`); a timer clears the toast only when its call was the last one, so a toast always stays six seconds from the last press |
| the tooltips of the disabled states ("Asking GitHub for the newest release" while *Checking…*, the disabled *Update to vX.Y.Z*) never showed: WPF hides a disabled element's tooltip (minor) | real | `ToolTipService.ShowOnDisabled="True"` on the footer button; `TheFooterAlwaysShowsTheButtonLeftOfLogAndTheStatusLineTrims` checks it |
| "Update now" did not wait for a stamp of the program icons that was running, and both probe the folder with the same file name (minor, in `LauncherModel.Updates.cs`) | real, narrow | `RunUpdateAsync` sets `_updateRunning`, waits until no stamp runs, then installs (the old body is now `InstallUpdateAsync`, unchanged); no stamp starts until the update is over (K43 section 7) |
| a personal build's Updates card said "a release would replace" her icon, which K43 made untrue (minor) | real | "Personal build: updates are off. It carries her face from the build itself; new versions are on the port's GitHub Releases page." |

Not unit-tested (they need WPF's dispatcher or the window): the toast timer and the tooltip on a disabled button; the update's wait for the stamp runs

## 7. One click (2026-11-01, after the review)

The user asked for the update to start from the button itself, "just like the Bloodborne launcher where you can just instantly update". A press of the gold
**Update to vX.Y.Z** now runs `RunUpdateAsync` right away (`PressUpdateButtonAsync`: `ShowUpdate` then `RunUpdateAsync`): the overlay opens on the download with
the release's title and notes, the progress and **Cancel**; a refusal (the game is running, the folder cannot be written) or a failure leaves the overlay with
**Update now** / **Try again** as before. A press of **Check for updates** that finds a release still opens the overlay with **Update now** / **Later**, since that
press asked only to check. The render no longer presses the button for `update_offer.png` (it would start an update); it puts the overlay in its offer state
(`PreviewUpdateState`). `--update-selftest` now closes the overlay the manual check opened (**Later**), checks the gold button is still there, and installs with
one press of it, so every real-launcher update test (UpdateEndToEndTests, UpdateButtonTests) goes through the one-click path.
