# K52: how fast earlier lines dim, and the text size in the owner's playthrough frames

Package K52, 2026-11-22, version **0.1.10** (branch `v0.1.10`, not released; the build still names itself 0.1.9). Fixes 3eb9ace and 99c6152. No game
data or story text was added.

## 1. The report

The owner gave two frames of a playthrough video labelled PS4, from the prologue `00_00` (scene 240): a cut-in up with no text (after message 313), and
313 grey above 314 while 314 is still typing; and a player's v0.1.9 screenshot at message 320 (318 and 319 grey, 320 white). Against the port played the
way New Game plays it, two things differed:

1. **Dimming speed.** In the frame 313 is already at the dimmed level (alpha about 0.39) while 314 is 25 characters in; the port took 153.6 frames.
2. **Text size.** The frame's glyphs are about 0.83 of the port's, its first line about 30 px lower, its lines 78.3 px apart against 81.55, and 313 wraps
   into 2 lines against 3.

The rest matched: the window darkening (the backdrop drops to 0.62 of its brightness in both, in the same pattern across the screen), the order at a
cut-in change (the text and the darkening fade out at the click, the picture changes, both fade back in with the earlier messages on the page), the
dimmed level, and the scene (it registers on the port's at a scale of 1.0000).

The issue #14 sweeps (K51 5, next-to-last item) showed one message per page and no window because `--script 30:scene=<id>` starts a scene directly
and skips START_SCRIPT (scene 110), which sets page mode (F822 = 1); New Game goes through it. Not a port difference. Pictures of text pages start
from `30:scene=110`.

## 2. Dimming speed (fixed)

Cause: the HUD (VA 0x53CF0) writes, every frame, `F[870 + j] = text speed - 128` for the message before the current one (j = min(F823, 11) - 2, the
0-based page position; VA 0x55C00..0x55C2E; config +0x20 unread or +0x22 read, by the current message's read flag 0x781AB0), and dims position j over
`(F[870 + j] + 128) * 1.2` frames (VA 0x55C37; 0x1A7120 = 128.0, 0x1A7124 = 1.2): 42 frames unread and 18 read at the boot speeds 35 and 15. The port
never wrote F870 and read `F[870 + F823]` once when a message started (and in the restore), one slot too far, so the limit was always 153.6 frames.

- 3eb9ace: the per-frame write and the limit, with the HUD's guards: the loop runs only with F822 == 1 and F1103 == 0; the timer advances only while the
  text fade is 1 (VA 0x55F8A) and becomes -1 once above the limit (VA 0x55FE2); config +0xA4 == 1 dims at once, also during a fade-in. A message whose
  text ends in `@k` takes the timer and limit of the next one that does not, and stays bright while that run reaches the current message (VA 0x55D01,
  0x55E86..0x55F52). The two early reads are gone. F870..F880 are in the history record's s8 list, so records and saves now carry the PS4's values; no
  format change, nothing reads them back, old saves behave the same.
- 99c6152 (the checker's finding): a click that completes a reveal set every timer of the page to -1, the current message's too, so the line the player
  clicked through went grey at once when the next one started, in the usual way of reading. The PS4 clears F823 - 1 words from F859 (memset, VA
  0xA27FC..0xA2830, wait_model.md 5.2): the earlier messages only. The port now does the same.

The frame does not pin the number: judging by how far 314 has typed, it is about 54 frames after 314's fade-in, so it rules out 153.6 but not a limit
up to about 54. The 42 comes from the eboot. knife's Switch code has the same 1.2 x text speed factor but takes the earlier message's own read
state, the eboot the current message's (VA 0x55C14): a read line above an unread one dims in 18 frames in knife, in 42 in the eboot and the port.

## 3. Text size (no change)

The port keeps its layout. The frame was very probably not drawn by the PS4 game the port follows (CUSA47999, app 01.01) but by the Switch overseas build:

- It matches knife's Switch English layout, which was fitted on Switch captures, not on this video, to within 0.5 px: glyphs 41.04 px (60 x 0.9 x 0.76,
  Helvetica Neue through nn::font), baselines 177.7 / 256.1 / 334.5 px predicted against 177.45 / 255.61 / 334.05 measured, line pitch 78.38 against
  78.30, left edge 96 px. The frame kerns: the 'o' sits under a 'Y' (0.69 of the port's advance for that pair, the same in two places).
- The PS4 eboot cannot draw it. None of its 337 imports is a font library; English comes from the `ft_en.mrg` bitmap pages with a fixed advance
  `(w - 6) * sx` and no pair table; no config field sets a text size or font; F31/F32, the only size words, are written by none of the 549 scripts, and
  the value that gives the frame's glyph size would put lines 72.6 px apart, not 78.3.
- Two PS4 sources agree with the port: the eboot under emulation (482 page glyph quads equal, K8; first English glyph top 109.69 px, pitch 81.55 px,
  text_vertical_scale.md 2, 6) and the English prologue movie in the PS4 data (glyphs at the atlas size, first line within 1 px, pitch 81.0 px;
  text_vertical_scale.md 7).

Port values, unchanged: scale 0.74 in every language, list 0x1E drawn at (1, 1.3) under 640 x 448 (81.55 px line pitch); English origin (30, 35) units and
width 574, Japanese and Chinese (87, 49) and 474; no kerning. Copying the frame would re-wrap every English page and needs a kerning vector font the PS4
build does not have.

Docs: 3eb9ace's message, textbox.md 5.8 and open question 7 and wait_model.md open question 5 called the frame a PS4 frame; K51 5 and compositing.md's
note on held layers did the same for the owner's frames of issue #14's scene, also from a playthrough video (probably the same one), so the issue #14
comparison is with that video, not with a PS4 capture. This package corrects textbox.md, wait_model.md, compositing.md and K51 5; the commit messages
stay as written. What the frames tell T04, and how to tell a PS4 frame from a Switch one: the T04 note in ps4_captures.md.

## 5. Not verified and not changed

- No confirmed PS4 capture: the dimming time on a console, T04's line pitch and the (1, 1.3) stretch stay unseen there. The `@k` rule comes from the
  code only; read text was checked by the tests and one second pass.
- Seen by the checker, not changed (small, older than this package):
  - Skip and fast-forward advance the dimming timer by the skip step (64 per frame); the HUD adds min(vsync count, 3) (VA 0x55FC1), so pages that flash
    past keep their earlier lines almost bright on the PS4 and grey them at once in the port.
  - The port reaches the floor one frame early (42 / 18 against 43 / 19): the HUD draws with the timer from before the frame's step.
  - The HUD skips the page block while the window fade (0xDF0730) or the HUD alpha (0x781148) is 0; the port keeps dimming while the hide-window action
    hides the page. Whether the PS4's hide zeroes either was not traced.
  - After a rewind to 313's page start the page shows no text until the next Enter, also in 6b263ad. A lead: `CmdMessage` pushes the history record
    before it sets F1103 = 0. Not compared with the PS4.
- Seen by the builder, not changed: the bright-or-dim level uses the window index (F1105 / F1109 >= 3) where the HUD tests F1111 >= 3 (VA 0x55C42); the
  port draws every message of its page list where the HUD draws min(F823, 11) - 1 earlier ones; whether the PS4 redraws earlier messages after a load
  was not checked (the port shows one).
- The video's scene sits 2.7 px higher than the port's; not explained.
- The old "78 px line pitch" lines still stand: FORMATS.md 7, RUNTIME_REQUIREMENTS.md 9.1 and textbox.md 10.1, whose errata text_vertical_scale.md 10
  lists, and ARCHITECTURE.md 11 #2, ROADMAP.md M2 (line 286) and the two strategy documents.
- Debug builds on one Windows PC (AMD); the Linux suites in WSL, headless, without the Render suite; no macOS. The game was checked in English only.
