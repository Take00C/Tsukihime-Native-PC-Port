# K11: memory growth (working set 2.2 -> 5.4 GB in a soak, 0.4 -> 1.9 GB in a paced play)

Package K11 of the knife-reference wave, run on 2026-10-26 on top of commit 49564e2 (the working tree also held other packages' uncommitted UI / input work; nothing of it touches memory). Nothing is committed.
All runs used a **hidden** SDL window, `--mute` and `SDL_AUDIO_DRIVER=dummy` (no sound was played); `artifacts/play`, `artifacts/play2` and `%APPDATA%\Tsuki` were never touched (every run used `--save-dir scratch\K11\...`
and `--game` on the read-only game folder, builds went to `artifacts\K11`); shadPS4 was not started. From the lead's message on the way: every build, test and soak ran at below-normal priority with `-m:4`, and no
frame-timing figure taken after it is used for a conclusion (section 8).

## 1. Result

| item | state |
|---|---|
| what grew | **the working set, not the heap and not the GPU**: memory-mapped archive pages (file cache charged to the process, up to the 40 GB of the archives) and, on top, a managed large-object-heap sawtooth made of evicted audio clips |
| real leaks found | none in the managed heap (live heap 436 MB -> 425 MB between two gcdumps 150 s apart), none in GL objects (GPU memory flat during 111,000 texture evictions), none in the texture cache, staging pool, look-ahead queues, script cache or history |
| fix 1 | the big archive mappings are dropped from the working set every 2 s by a below-normal thread (`GameFolderSource.TrimMappedPages`, `Tsuki.Platform.MemoryPages`, `MappedFile.TrimResident`) |
| fix 2 | `ClipCache` asks for a background generation-2 collection after every 128 MiB of decoded PCM, so evicted clips are freed on a schedule instead of piling up on the large object heap |
| diagnostics | `--mem-log N` (process / managed / cache figures every N s, allocation sampling by type and thread) |
| fast soak, 400,000 steps | working set **3.2 -> 5.7 GB, still rising** before; **0.8 .. 1.2 GB, mean 1.02 GB, no trend** after (30 s samples in section 6) |
| paced soak, 60,000 steps | working set **0.49 -> 1.94 GB, still rising** before; **0.43 -> 1.0 GB** after, nearly flat once the texture cache is full (last two minutes +7 % / -3 %) |
| longer check | **1,000,000** fast steps (959 s): 0.84 .. 1.31 GB from 60 s to the end, mean 1.04 GB, sd 7.6 %, no trend |
| tests | Synthetic **873** (7 new), Data **1108**, Render **72** (2 new; `UploadTimingTests` excluded): all pass |

## 2. Method: split the process

Three instruments (all local to `scratch/K11`):

* `--mem-log N` (new, `GameApp.LogMemory`): working set, private bytes, `GC.GetGCMemoryInfo` (heap, committed, fragmentation, gen0/gen1/gen2/LOH/POH sizes, collection counts), the engine's caches
  (textures, spare pool, staging pool, feeder queues) and, from an `EventListener` on the runtime's `GCAllocationTick`, the biggest allocators by type, heap kind and thread.
* `scratch/K11/vmtool`: `VirtualQueryEx` + `QueryWorkingSetEx` over a live process: committed and **resident** bytes of its private, mapped-file and image memory.
* the Windows `GPU Process Memory` counters (dedicated / shared / committed of the process), sampled every 5 s with the working set (`scratch/K11/soak.ps1`).
* `dotnet-gcdump` 10.0.750501 and `dotnet-counters` as local tools in `scratch/K11/tools` (two gcdumps, section 4).

## 3. What grew

### 3.1 Fast soak, before (`--hidden --mute --fast --autoplay click --choices random:7 --exit-after 400000`, idle machine, build of 49564e2 + the log flag)

`scratch/K11/vm1`, the resident part of each kind of memory, MiB:

| s | private resident | **mapped-file resident** | total resident |
|---:|---:|---:|---:|
| 20 | 1981 | 821 | 2852 |
| 41 | 2374 | 1569 | 3994 |
| 61 | 1935 | 1929 | 3914 |
| 82 | 1495 | 2302 | 3848 |
| 102 | 1564 | 2661 | 4276 |
| 123 | 1672 | 3123 | 4846 |
| 144 | 2093 | 3471 | 5615 |
| 165 | 2184 | 3642 | 5878 |
| 187 | 2363 | **3842** | 6256 |

The mapped part grows **linearly, about 3 MB/s**, for as long as the run reads new pictures and clips; private resident goes up and down between 1.5 and 2.4 GB. The archives are mapped whole
(`MappedFile`, 24 GB for `allpac1`, 40 GB in all) and a page that a decode touched stays in the process's working set until the system needs the memory. Nothing leaks, but the working set of a long play
grows by everything the game ever read, bounded only by the size of the archives; Task Manager's details tab and the lead's script (`WorkingSet64`) show it.

Other series of the same run (`scratch/K11/base_fast`, 5 s samples; MiB):

| | s=37 | 67 | 97 | 127 | 157 | 188 |
|---|---:|---:|---:|---:|---:|---:|
| working set | 3564 | 3618 | 3791 | 4928 | 4939 | 5320 |
| private bytes (commit) | 5180 | 4626 | 4420 | 4831 | 4634 | 4603 |
| GPU dedicated | 2908 | 2974 | 3090 | 3122 | 3152 | 3160 |

* **Commit** (private bytes) is 4.2 .. 5.3 GB and **flat**: most of it is the AMD driver's reserve and is not resident.
* **GPU memory** rises to 3.15 GB in the first 120 s and then **stays flat** while the cache evicts 111,000 textures and recycles 60,000: no GL object leak.
* **Managed heap**: 0.74 .. 1.96 GB committed, saw-toothed (`scratch/K11/vm2`), live set after a full collection about 430 MB (section 4).

### 3.2 Paced soak, before (`--autoplay click`, 60,000 steps, real movies, `scratch/K11/base_paced`)

Working set: 492 MB at 37 s, 504 MB at 127 s (the opening movie), 626 MB at 428 s when the first pictures load, 1.15 GB at 579 s (texture cache full: 3,100 textures, 1535 MiB), then **1.26 .. 1.94 GB rising
until the end** (1000 s). After the cache is full the textures no longer grow the process; the rest is the same two things as above, measured in the fast soak: archive pages and the managed sawtooth
(managed committed 0.16 -> 0.91 GB over the run; the other +0.4 GB is by difference mapped archive pages, as in the fast soak: I ran the vm tool on the fixed paced build only, where the mapped part stays at 17 .. 21 MiB).
The first 6 minutes (the movie) creep by 43 MB (0.1 MB/s); that is generation-0 allocation before the first collection (`allocated` rises by the same 41 MB, the committed heap stays 161 MB), not a leak.

### 3.3 Where the managed churn comes from (allocation ticks, fast soak)

Per 30 s: `System.Single[]` on the large object heap 200 .. 600 MiB (the decoded PCM of clips: each voice line, effect and track is one array), `Text.Quad[]` 100 .. 450 MiB (a `List<Quad>` per text block per
step, generation 0), `Byte[]` on the LOH 30 .. 60 MiB. The clip cache holds 256 MiB at most (`ClipCache` evicts correctly, verified, section 7), but an evicted clip is freed only by a generation-2 collection, which the
collector schedules from its own budget: between two of them the large object heap held 0.5 .. 1.1 GB, with up to 570 MB of fragmentation.

## 4. What does not grow (ruled out with evidence)

| suspect | result |
|---|---|
| managed live heap | `dotnet-gcdump` (each dump forces a full GC) of the fixed build at 100 s and 250 s of a fast soak: **436,423,792 -> 424,609,447 bytes**; the largest objects are byte-identical (2 x 15,531,504 B `Int64[]`, 2 x 12,767,826 B = the eboot twice) except the PCM arrays, which follow the clip cache. `scratch/K11/report_final_a.txt`, `_b.txt` |
| GL objects | GPU dedicated memory flat at 3.1 GB from 120 s to the end of a 200 s fast soak that evicted 111,000 textures (and 3.04 .. 3.25 GB over the 959 s, 1,000,000-step run); every `GenTexture` / `GenFramebuffer` / `GenBuffer` in `src` has a delete (`TextureCache.Retire`/`Dispose`, `GpuCompositor.Dispose`); the render targets are keyed by id and created once |
| `TextureCache` + spare pool | bounded by `capacityBytes` (1536 MiB) and `SpareCapacityBytes` (256 MiB); new test over 3,000 uploads of six shapes asserts both caps after every upload. Graded variants are separate keys in the same LRU |
| `StagingPool` | `peak total 63 MiB` (budget 64) in every run, `outstanding 0` at every log line after a decode burst; new test with four renters of mixed sizes |
| look-ahead / grade queues (K8) | `queued set`, `wanted`, `feeder pending` are 0 at rest and a few hundred at most during a load; the scheduler's background queue is bounded by the staging pool |
| `ClipCache` (K10 fix) | `Bytes <= budget` after every request over 6,000 requests of mixed sizes and over 12,000 from 8 threads (new tests) |
| scripts | all 549 scripts decoded: **18 MiB** (23 MiB with the label tables), `scratch/K11/scriptsize`; the cache keeps them all, bounded by the game |
| history / backlog | the 800-record ring; the managed live set does not move with the step count (1,000,000 steps) |
| glyph pages, UI sheets, geometry caches | keyed by language / sheet / picture: bounded by the game's content (tens of entries in the dump) |
| movie buffers | the opening movie phase grows only by gen-0 allocation (section 3.2); every `av_packet` / `av_frame` is freed or unref'ed in `MoviePipeline`, `FfmpegMovieIo`, `MovieQueues` |
| native decoder contexts | `Atrac9Decoder` frees frame, packet and context in `Dispose`; `DecodeAll` is in a `using` |

Grow-only tables that are bounded by the scripts, not by play time: `GradeKeys` (one key per distinct colour grade), `TextureCache._transition` (the rule textures), `GameApp._reportedMissing` (a log de-duplication
set, empty in a normal run). I left them alone.

## 5. Fixes

| file | change |
|---|---|
| `src/Tsuki.Data/Containers/MappedFile.cs` | `TrimResident(Action<nint, nuint>)`: hands the whole mapping to the trimming function in pieces of at most 1 GiB (Tsuki.Data makes no P/Invoke, `DataAndEngineMakeNoPInvoke`) |
| `src/Tsuki.Data/Containers/MrgArchive.cs` | `MappedLength`, `TrimResident` |
| `src/Tsuki.Data/GameFolderSource.cs` | `PageTrimmer` (set by the shell) and `TrimMappedPages()`: for every opened archive of 128 MiB or more (the image, audio and voice banks; the scripts, fonts and tables stay) it calls the trimmer, under the same lease as a decode (`UseGate`), so `Dispose` still waits for it |
| `src/Tsuki.Platform/MemoryPages.cs` (new) | `TrimResident(address, length)`: `VirtualUnlock` on pages that are not locked, which removes them from the working set (the error it reports is the normal result); no-op off Windows |
| `src/Tsuki.App/Play/GameApp.cs` | `StartPageTrimmer`: thread `tsuki-trim`, below normal priority, every 2 s, joined before the source is disposed; counters in the memory log; `--mem-log` hook |
| `src/Tsuki.Media/Sound/ClipCache.cs` | `collectEveryBytes` (default 128 MiB) and `collect` (default `GC.Collect(2, Forced, blocking: false)`): after that much decoded PCM a **background** generation-2 collection is requested, outside the lock; `Collections` counter |
| `src/Tsuki.App/AppArgs.cs`, `Play/MemoryProbe.cs`, `Play/AllocationSampler.cs`, `Play/TextureFeeder.cs` | `--mem-log SECONDS`, the figures above, `TextureFeeder.Pool` / `DescribeQueues` |

Why trimming is safe and cheap (`scratch/K11/trimtest`, `allpac1.mrg`, 23 GB view, 1.9 GB of it touched): `VirtualUnlock` over the whole view **271 ms** (about 0.14 ms per MiB that was resident), **3.4 ms** when
nothing is resident; the trimmed pages go to the system file cache, so a second read of the same 2 GB took 634 ms (soft faults) against 2,810 ms for the first. In the game the thread's calls cost 8.8 ms on
average in the fast soak (194 calls, 1,715 ms in all, longest 32.7 ms) and 0.9 ms in the paced one (509 calls, 461 ms, longest 11.5 ms) and run on their own thread: the main thread never waits for one, and a decode that reads
a trimmed page takes a soft fault, not a disk read. The effect on the working set is immediate: mapped resident stays at 18 .. 100 MiB for the whole run (`scratch/K11/vm2`, `vm3`) instead of reaching 3.8 GB.

Why the collector nudge: the 128 MiB period bounds the garbage on the large object heap to one period plus the cache; it costs a background collection per 128 MiB decoded (every 5 s in the fast soak, every few
minutes in play) and no pause on the calling thread (`blocking: false`).

**Tried and reverted:** `StagingPool.Rent` only drops free buffers of other sizes when the renter already fits, so a renter whose size differs from every free buffer waits until the pool is empty (a test with
mixed sizes and a single thread hangs on it; with several threads it resolves when the upload thread returns buffers). I fixed it, but the soak showed what the old behaviour hides: 28,248 pinned-array allocations
(each pre-touched) against 317, because tiles of different pictures have different sizes. That is churn on the pinned heap for a stall that only exists with mixed sizes, so I put the original back and wrote the test
so that it does not depend on it. A size-class design (buffers rounded up to a few classes) would fix both; it is not memory work.

## 8. Not measured, and what is left

* **Frame times.** The K8 hitch work is untouched (no change in the stage, look-ahead, feeder, upload or compositor code), but I could not re-measure it: the machine ran a game, the paced soaks ran next to builds and GPU tests,
  and the lead asked not to use timing now. Two paced runs after the fixes: `vm4_paced` (14 frames over 33 ms, all in the opening-movie phase, none in the picture phase) and `final_paced2` (207, 203 of them in one
  90 s window at steps 31,700 .. 34,000 whose time is `execute` / `present`, the GL calls, which is when the 4-minute Data test run was reading the archives and decoding next to it). The paced run before the change, taken before the lead's message (next to other soaks), had 2. Re-run the paced soak
  once the machine is quiet; the figures to compare are `frames: ... over 33 ms` in `log.txt`.
* **`Text.Quad` lists** (`BlockDraw.BlockQuads`): a new `List<Quad>` per text block per step is the biggest generation-0 allocator (100 .. 450 MiB per 30 s in the fast soak, 0.5 MB/s in play). Reusing the list per block would
  tighten the heap's sawtooth further; it is engine text code, so I left it.
* **Texture cache size.** The cap counts RGBA bytes (1536 MiB) but the driver holds about 2.4 .. 3.1 GB for it on this GPU (padding, per-object overhead); on a smaller card, lower `TextureCache`'s capacity in `GameApp.OpenRenderer`.
* Windows only: `MemoryPages.TrimResident` does nothing elsewhere (a `madvise` branch would do the same on Linux; untested here, so not written).
