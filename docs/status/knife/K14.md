# K14: the title with no logo and no menu after a screen was closed (stuck backdrop), W S A D in the menus, any key

Package K14, run on 2026-10-26 on top of commit 21f289b. Trigger: the user's screenshot of the windowed Release build (`artifacts/play3`): the title shows only the moving
background and the copyright; the logo and the menu "appear only while the mouse pointer is exactly over where they should be", and keys do not help.
Everything below was run with hidden windows, `--mute` and `SDL_AUDIO_DRIVER=dummy`, at below-normal priority; `artifacts/play`, `play2`, `play3` and `%APPDATA%\Tsuki`
were not touched (`--save-dir scratch/K14/saveA`, a copy of K13's `saveF`), builds went to `artifacts/K14`. Nothing is committed. Other packages' uncommitted files in the same
tree (K15: `AppArgs.cs`, `GameApp.cs`, `InputScript.cs`, `AutoPlayer.cs`, `PlayCommand.cs`, `FlowExplorer.cs`, `SweepRecorder.cs`) were not edited by this package.

## 1. What was wrong

**Reproduced in the real app** (build of 21f289b, Release, hidden window, scripted keys, no pointer): boot notice, intro, title: logo and menu are there (also with a pointer inside the
window, in hold mode `TSUKI_HOLD`, and in ja / zc / zt). Open CONFIG (or LOAD GAME) from the title and go back: the title is left with **only the background, the dim copyright, the
leafy cloud strips along the top and bottom edges and the drifting sparkles**; no logo, no menu. A key press makes the logo and the menu flash for about a second and vanish.
`scratch/K14/cB.png` (frames 1000, 1150 config, 1300, 1400, 1440 after one Down, 1500) is the same picture as the user's `Screenshot 2026-10-26 205000.png`.

**Cause.** `ConfigScreen.OnOpened` and `SaveLoadScreen.OnOpened` fade the submenu backdrop in (`Backdrop.Fade(0.02)`) when they open over the title. Nothing fades it out again when they
close back to the title (the system menu, the gallery and `TitleScreen.ReturnFromGallery` do; these two did not). `TitleScreen.StepFx` counts a visible backdrop as a screen covering
the title (the PS4: the logo alpha falls at 1/60 per frame while the overlay fade `0xE2377C` is above 0 or the movie is paused, system_flow.md 4.5.1), so the logo alpha fell to 0 and stayed
there; the menu items and the glow are multiplied by it. Every cursor change snaps the logo to 1 (the PS4 does too) and it then falls again over 60 frames: that is the "appears
while I move" of the report. It is not about the mouse: a key does the same. The user most likely pressed Enter or clicked on CONFIG or LOAD GAME and came back; I could not read the
user's profile (not to be touched), so that route is inferred from the picture.

The same stuck state could also arise from the story's system menu: its "Return to Title" path closes through `Clear()`, whose `OnClosed` does not cut the backdrop (the real app ran this
route fine, shot `scratch/K14/cD_K14.png`; the new title now starts clean regardless, 3.1).

## 2. What the PS4 does

The system state machine's title re-entry (VA 0x68B7F) sets the overlay rates to -0.02 and resumes the movie (system_flow.md 4.5.1): after LOAD GAME / CONFIG the backdrop fades out over
50 frames **over the visible title**, the logo (already at 0 while the screen covered it) fades back over 121 frames and every menu input snaps it to 1.

## 3. The fix

1. `TitleScreen.OnOpened`: `Backdrop.Reset()` (new, `UiBackdrop.Reset`: alpha, speed, strip animation and sparkles to zero). A title starts from nothing; whatever an earlier screen left up is gone.
2. `TitleScreen.ReclaimTitle` (every step, while the title is the top screen in FadeIn / Idle): a visible backdrop that is not already fading out gets `Fade(-0.02)`, the PS4's re-entry rate.
   The logo and menu come back behind it (about 3 s, the PS4's own timing).
3. **Wake** (the user's addition): in Idle, **any pointer move anywhere in the window, a click, the wheel, a key, a pad button or a direction** cuts a backdrop that is still going and snaps
   the logo alpha to 1, so the logo, the glow and the menu are on screen at once. The cursor does not move unless the pointer is over an item, so a pointer in an empty corner only shows
   them. (The initial fade-in is left alone: the wake needs the menu up.)
4. **Any key means any key** (the user's PRESS ANY KEY): `PcInput` also reports "some key is down" for keys the game binds to nothing (`PcKey.Other`, `ShellActions.AnyKey`, an edge
   once per press). `UiInput.Any` already counted every shell action, so the boot notice, the intro and caution skips, PRESS ANY KEY, the popups and the wake all take G, Shift, F1 ...
   too. (Before, only the bound keys counted, which is why "any key" did nothing for most keys.) The story ignores the new bit.
5. Nothing else changed in the title's flow: hover moves the cursor only when the pointer moves onto an item, a click on an item acts, a click elsewhere does nothing, Enter decides the cursor
   item; the cursor starts on CONTINUE (NEW GAME without a save).

PRESS ANY BUTTON (G010 = 0, prologue read): checked on the real sheets, `PressAnyKeyShowsItsTextAndAnyKeyOrClickAdvancesIt`: the keyboard style draws PRESS ANY KEY (11 glyph quads
plus outline copies, blinking 0.1 .. 1 with a 120-step period) and an unbound key or a click moves it to the first caution. The prompt ignores input until the fade-in has finished
(121 frames, PS4 state 4 comes after state 1); a pad button is covered by the existing synthetic test (`PressAnyButtonLeadsThroughBothCautionsToTheStory`, Decide).

## 4. W S A D in the menus (the user's addition)

`InputMapper` keeps the arrow keys exactly as they were and puts the letters in **three new menu-only fields** of `InputFrame` (`MenuHeld`, `MenuPressed`, `MenuRepeated`: the d-pad bits
the letters stand for, with the d-pad's repeat delay 24 and period 6). `UiInput.From` adds them to Up / Down / Left / Right and their "newly pressed" flags and to `Any`. The story,
the host and the choice code never read them. `AppRuntime` strips them from the frame of the step in which a menu opens (like the other presses).

| key | menus (every `UiScreen`: title, system menu, lists, config, gallery, dialogs, popups) | story |
|---|---|---|
| W | Up | nothing (Up still opens the mode panel; W does not) |
| S | Down | nothing |
| D | Right | nothing |
| A | Left | **still toggles auto mode** (`ShellActions.AutoToggle`); in a menu the same press is Left and the menu ignores the shell action |

Clashes found and how they were settled: A is auto mode in the story (kept; menus read it as Left only while a menu is open: `AppRuntime` hands the story the pad bits, not the menu
fields); W / S / D had no binding; Q / E (tabs), H, M, N, B, V, I, X, Z are unaffected; the story's own choice list and yes / no prompt keep the arrows only (a letter there would clash with A);
the guide line of the story prompt (`GuidePrompt`) therefore shows no letter caps. The keys are listed in `PromptBindings.Keys` (so the K9 test that every key of every action does what
the action says covers them), in `InputMapper.Bindings`, in the README table and on screen:

* **Guide line (keyboard style)**: every "Navigate" / "Move Cursor" icon now has the letter cap beside the arrow cap: `WASD` (all four), `A D`, `W S`, `W`, `S`, `D`, `A` for the one- and
  two-direction icons (`scratch/K14/ui/ui_guides_en_keyboard.png`; the story prompt's guide `ui_story-prompt-cursor_en_keyboard.png` has none).
* **Controls tab**: its rows are the story's controls (control panel = Up, advance = Down, auto = A ...), which did not change, so the rows and their caps are unchanged; the menu
  keys are shown by the guide line of every menu, including the Controls tab's own (`WASD` after the arrows in `scratch/K14/shotsE/e1250.png`).
* README: new row "W, A, S, D"; the button-prompt paragraph names them.

## 5. The other menus (the "hover-only" check)

Real app, no pointer, keys only (`scratch/K14/cC.png`, `cE.png`, `cF.png`, `cG.png`): the **load list from the title** (slots, preview, guide), the **gallery hub** (CG grid, side list
with the first mode highlighted), the **system menu in the story** (all five tabs and the title bands visible, the cursor light on Save), a **sub menu over it** (Load highlighted, list
visible) and the **config screen** show every item with no pointer; none of them hides anything until it is hovered. Hover and clicks work as before (hover at (960, 869) took LOAD GAME, a click at
(960, 925) opened CONFIG, `cF.png`). One observation, left as it is: in the system menu the cyan "hover" column of the cursor tab starts only after the first key or pointer move
(`_focus`); the cursor light and line, and all five tabs, are visible from the first frame. The data does not say whether the PS4 highlights the first tab at once.

## 8. Open issues

1. Nothing was run with a real mouse on a visible window (rules): the pointer path SDL -> `Viewport` -> `PointerState` is the one K12 unit-tested; the scripted pointer drives the same fields.
   The user's exact route to the stuck title is inferred (CONFIG or LOAD GAME and back); the fix covers both and the system menu's return.
2. `AnyKey` is an edge for the first key that goes down while no key was down; a second key pressed while one is held makes no new edge (so holding Ctrl and pressing G counts once).
   A gamepad button counts through the pad bits as before; Alt+Enter (fullscreen) also counts as a key press.
3. The logo still takes about 3 s to come back by itself after CONFIG / LOAD GAME (50 frames of backdrop, 121 of logo, the PS4's timing); any input shows it at once.
4. The system menu's cyan tab highlight before the first input (section 5) and the story's choice lists taking arrows only are choices left as they were.
