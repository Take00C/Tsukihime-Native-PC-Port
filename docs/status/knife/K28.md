Package K28 (label `k28`), run on 2026-10-30 on top of commit f74a533 plus the uncommitted K24 (screenshot key), K25 (other dumps) and K26 (`docs/PUBLISHING.md`).

## 2. The PERSONAL build (request 2)

**What it is.** `-p:TsukiPersonalIcon=<game folder>` on a build or publish of `Tsuki.App` or `Tsuki.Launcher` (or the solution) puts the Arcueid close-up of
K23 into the icon resources of `Tsukihime.exe` and `TsukihimeLauncher.exe`, so Explorer shows her face on the files themselves. `src/Tsuki.PersonalIcon.targets`
(imported by both csproj files after their `Version`) does, before the compile of each program: restore and build `Tsuki.Cli` (with the build's own global
properties, so a solution build shares its one build of the Cli), run **`Tsuki.Cli face-icon --game <folder> --out <obj>\personal`** (the new command: `FaceIconCache.Ensure`
into that folder, i.e. the very code the game and the launcher run at start; `--force` rebuilds; a folder that is not the game or has no usable picture exits 1 and
the build stops with TSUKI011 instead of falling back to the crescent), and set `ApplicationIcon` to `<obj>\personal\icons\tsukihime.ico` (git-ignored: `.gitignore`
has `obj/` and `artifacts/`; `git check-ignore -v` names those lines for both the plain and the `--artifacts-path` location; `git status` shows no `.ico` or `personal`
path). Without the property the file does nothing: the crescent stays and no mark is written.

**The marks** (all three, so that none can be forgotten): `[assembly: AssemblyMetadata("TsukiPersonalBuild", "true")]` and the informational version
`1.0.0-personal+<commit>` (static `AssemblyMetadata` item and `InformationalVersion` under the property's condition; `AppIdentity.IsPersonalBuild` reads the
attribute and the game logs `personal build: the executable carries the Arcueid icon cut from the owner's copy of the game (package K28); this build must not be shared`
after its version line), and **`PERSONAL_BUILD.txt`** beside the programs (five lines saying what it is and that it must never be shared; written into obj/ by the
game's project only and copied as a `None` item to the output and the publish folder; the launcher's folders get it with the game's files through the project
reference, `TsukiCopyAppOutput` and `TsukiPublishApp`; a second copy from the launcher's own obj/ was a duplicate publish item, NETSDK1152, in the first attempt). A later
build without the property into the same output removes the note again (IncrementalClean; verified).

**The refusal.** `Tsuki.Cli release-check <folder> [--icon FILE] [--dump DIR]` (`ReleaseCheck.Run`): the folder must hold `Tsukihime.exe` (a wrong path fails, it
does not pass), no `PERSONAL_BUILD.txt` anywhere under it, the icon group 32512 of `Tsukihime.exe` and `TsukihimeLauncher.exe` must decode to the same frames as
`assets/icon/tsukihime.ico` (the crescent; default `--icon` is the repository's file), and `Tsukihime.dll` / `TsukihimeLauncher.dll` must carry neither the metadata key
nor a `-personal` version. `--dump` writes a PNG per frame of what the executables really carry. The reading is `src/Tsuki.Data/Icons/PeIcons.cs`: the PE headers
through `System.Reflection.PortableExecutable`, the resource tree (type RT_GROUP_ICON 14 / RT_ICON 3, id, language, data entry) walked here and the group rebuilt into
.ico bytes for `FaceIcon.DecodeIco`; the attributes decoded with `System.Reflection.Metadata` (no Win32 call, no load). Documented in `docs/PUBLISHING.md` (0.4, the
"never" table, the new 1.4, step 4.1.6) and README ("Personal build").

**Moved:** `FaceIcon.cs` (FaceIcon, IconFrame, FaceCrop, FaceIconCache) went from `src/Tsuki.App/Play` to **`src/Tsuki.Data/Icons`** (namespace
`Tsuki.Data.Icons`; `git mv`, history kept), because Tsuki.Cli may not reference Tsuki.App and a linked copy would have made the type ambiguous in `Tsuki.Tests.Data`,
which references both. The launcher and the Render tests no longer link the file; the call sites use the new namespace. Tsuki.Data's no-whole-file rule
(`LvAndBuildCheckTests.TsukiDataNeverReadsAFileWhole`) made `FaceIconCache` read the stamp's first line with a `StreamReader` and the icon file through a `FileStream`
capped at `MaxIconBytes` (4 MiB).

## 6. Open issues

1. The gaps were measured on renders, not looked at on a monitor (no window was shown): 28..31 px between items, 34..37 above the copyright, 33 under the Japanese
   subtitle. If the lead wants CONTINUE further from the subtitle, `SixRowTop` back to 298.667 with `SixRowPitch` 19.6 still gives 32 px above the copyright (the
   test asks for at least the item gap + 2).
2. The item art's ink varies by a few rows per word (CONFIG is 14..16 rows), so the measured gaps vary by 3 px; the nominal rows 28..46 are what the code and the test use.
3. A personal build's first compile builds and restores Tsuki.Cli from inside the game's build (one extra restore + build, a few seconds; the icon itself 0.3 s and
   then `(current)`); a release build is untouched. The launcher's WPF window resource (`Assets\tsukihime.ico`, the fallback before a folder is known) stays the crescent
   in a personal build; its window takes the profile's Arcueid icon at run time as before.
4. `release-check` compares the 32-bit BMP entries of the icon groups; a PNG-compressed entry (the crescent's 256 px one) is not decoded and not compared. A personal
   icon has seven BMP entries, so the count alone already differs; a future crescent with only PNG entries would make the check report "could not be read".
5. The personal marks are read from `Tsukihime.dll` / `TsukihimeLauncher.dll`; a single-file publish (not used by the port) would hide them inside the bundle, and only
   the icon group and the note would remain checkable.
6. The window-size screenshots were measured at a lower ink threshold (165) than the canvas renders (205) because the downscaled serif art is dimmer; the rows agree with
   the canvas within a pixel.
