# K16: polish and user-flow bug hunt

Package K16, run on 2026-10-27 on top of commit aa4a720. Trigger: the game is playable end to end; this round plays what a player does (title, save / load, quick save,
rewind, backlog, config, skip / auto, choices, gallery, flowchart, window) in the real `Tsuki.App` with scripted input and looks at the result, then three polish items.
Every run used a hidden window, `--mute`, `SDL_AUDIO_DRIVER=dummy`, below-normal priority, `--save-dir scratch/K16/...`; builds went to `artifacts/K16`.
`artifacts/play*`, `artifacts/dist`, `%APPDATA%\Tsuki` and the game folder were not touched. Nothing is committed.

## 2. How it was done

New verification verbs (`InputScript.cs`, `AutoPlayer.cs`; header comment of `InputScript.cs` lists them): `pad=Button[*steps]` (a gamepad button through the real `InputMapper`: South / East /
West / North or Cross / Circle / Square / Triangle, L1, R1, L2, R2, Start, Back, Up, Down, Left, Right), `holdchoice` / `releasechoice` (the autoplay leaves an open choice list to the script).
`log` now also prints the config (`cfg [lang bgm se sys voice unseen seen auto ffRead endInstant anim win]`), G10, the open choice kind, the audio plays posted and the last voice.
A run is `scratch/K16/run.sh NAME SAVEDIR SCRIPTFILE --fast ...` (script files in `scratch/K16/s_*.txt`, git-ignored), each checked with a screenshot sheet and `scratch/K16/lg.py`.
Frame numbers: the boot notice ends at about 350, the title menu is up at about 1450 (with an intro movie in the way), the first story page of a fresh profile at about 2000.

## 5. Polish

### 5.1 The system menu's blurred backdrop (done)

The PS4 / knife blur the frozen scene behind the system menu and the backlog (engine-writeup "In the game": a captured frame, blurred over two frames; knife `game.rs` `menu_blur`,
`knife-render` `fs_blur`; the overseas build blurs a half-size copy: sigma 1.25 taps of 1.567 half-size pixels, about 3.9 full-size pixels, and scales it up; the blurred picture's alpha
rises by 1/12 a frame). Ours:

* `QuadPass.Blur` (additive, `DisplayList.cs`): one separable gaussian pass. `A0, A1` = tap step in uv, `A2` = sigma (in taps), `A3` = n (taps each side). `CompositorShaders` (mode 0, `u_fx.z` and `u_blur`), `GpuCompositor.DrawQuad` and `CompositorProgram.Blur` set it up.
* `Tsuki.Ui/Framework/UiMenuBlur.cs`: four commands before anything of the menu is drawn: capture the scene drawn so far (surface 12), blur it along x into offscreen target 40, capture that (surface 13), blur it along y over the frame at the fade alpha (blend state 1). Sigma 4.4 pixels, 13 taps each side, full size (the half-size upscale of knife adds about the same softness). The stage uses surfaces 0, 8..10, 15 and targets 1..3, 8, so nothing is disturbed.
* `UiRoot`: `BlurAlpha` (0 when no system menu or backlog is open, +1/12 a frame while one is: 12 frames to full), `Draw` appends the blur while `BlurScene` is true (which already hid the message text). It is recomputed every frame from the frozen scene (no persistent blur surface), a GPU cost of about 54 texture fetches per pixel; the draw time of a hidden 2,200 frame run with the menu open stayed at 0.54 ms mean (CPU submit time only; the GPU time was not measured).
* Proof: GPU test `PassTests.ABlurPassMixesTheTexelsAlongItsAxisByTheirGaussianWeights` (both axes, edge texels equal the weighted sums, far texels unchanged, over-blend at half alpha); synthetic `MenuTests.TheSceneBehindTheMenuIsBlurredAndTheBlurFadesInOverTwelveFrames` and `TheBlurEndsWithTheMenuAndStartsFromNothingAgain`; real app: `scratch/K16/bl` (system menu at frames +3, +20, +70 and the backlog: soft window frame, the menu text and tabs sharp).
* Not done: the closing fade keeps the blur until the menu leaves the stack (knife fades the backdrop and cuts the blur at the end of the 30 frame close; same result), no separate Overseas / Japan variants.

### 5.2 Saves made from the SELA prompt had a black thumbnail (fixed)

The prompt's own frame is the black start of a chapter. `AppRuntime.NoteStoryFrame` now grabs the frame of the page being read (a message fully shown in an open window, not skipping, not a choice or movie), at most once in 180 steps; the grab of the last
*bright* page (mean luma >= 14 of 255) is kept for 6,000 steps, because a chapter ends on a dark page. The save screen opened from a prompt takes that frame (`_heldThumbnail`) instead of the black one; the memory is dropped
when the story, the host or a restore changes. A save from the system menu is unchanged (it grabs the frame at the moment of the key). Proof: `StoryPromptAppTests.ASaveFromThePromptCarriesTheLastPageThatWasReadNotTheBlackChapterStart`
(a fake grab: bright while reading, black afterwards, the saved slot is bright); real app, fresh profile to chapter 2 in click mode (`scratch/K16/sela1`, 78,300 steps): the slot shows the last bedroom page with its text, not black.

### 5.3 Scenes 14_01B: unsure grade / blend look (looked at, no change)

K15 flagged frames of `14_01B_02_CIEL14B_3`, `3B`, `4`, `14_01B_03_CIEL14B_4_1x`, `5B`: saturated pink / red with large near-white areas. I played scene 771 (`3B`) from `scene=771` in the real app (1,920 x 1,080 shots every 200 steps,
`scratch/K16/b3`) and dumped the display list of the flat red frame (`TSUKI_DUMP_FRAME`, `scratch/K16/b3d`). What is drawn there: 128-tile pictures of archive 0 (190, 187, 1061, 1063) in effect words 5 and 17 (the dodge / ps_dodge5 shaders) at alpha 0x57..0xC3
over graded pictures of archive 1 (grade key 16), with the full-frame `Pic(0,352)` (25 tiles, effect 17 at alpha 0x14, then effect 0 opaque) last; the flat red frame is that last picture drawn opaque, i.e. its content, not a runaway blend. The blend shaders are
compared with the PS4's own shader code (`ComposeDifferentialTests`) and the STEC kernel with the engine's function under emulation (K7: 336 cases), so what is left is the script's choice of layers and strengths, which no PS4 capture can settle here. No code change.
