# K23: the Arcueid icon, and text for text hookers (GDI hook point, WebSocket feed)

Package K23 (label `k23`), run on 2026-10-30 on top of commit 1eb9775 plus the uncommitted packages K20 (icon, title, Tsukihime.exe, shortcuts) and K21 (screenshot key,
background mute, close question, Copy Text to Clipboard, opacity). Nothing is committed. Builds in `artifacts/k23` (Release, `-warnaserror`, 0 warnings), temporary profiles
under `scratch/k23/` and the test runner's temp folder, every game run hidden and muted (`--hidden --mute`, `SDL_AUDIO_DRIVER=dummy`) on its own `--save-dir`, the launcher
only in its offscreen modes (`--selftest`, `--render`) on a temp `--data` profile with temp shortcut folders. No window was shown. `artifacts/play*`, `artifacts/dist`, the user's
`%APPDATA%\Tsuki`, the real desktop, Start menu and clipboard, and the game folder (read-only) were not touched. No knife file was translated (`ConfigScreen.cs`, edited here,
carries its MPL header since K5a and is listed in `docs/THIRD_PARTY.md`; knife's `text_stream.rs` was read for its behaviour only, the server here is written from RFC 6455).
No game art is committed: the icon is built at run time from the player's files into the profile folder, and the pictures below live in `scratch/` (git-ignored).

## 1. The Arcueid icon (request A)

**The source.** Of the 499 A-size Arcueid face records in the catalog (`scratch/k23/probe/aru_a_records.txt`), `ARU_A_00_00_N00` (pose 00, costume 00, expression N00: her
neutral smile, the sprite of her first appearances) was chosen: its face layer `ARU_A_00_00_N00.MZP` (allpac1, 1270 x 1020 displayed) is **her whole head at sprite
resolution** (the opaque box is 933 x 1020: hair top to collar), drawn over the body `ARU_A_00_00_N00_B.MZP` (1778 x 6630) as the engine does (images.md 7). The face layer
alone has holes where the body's hair shows through (`scratch/k23/probe/face_layer_only.png`: the top corners), so the body's tiles under the square are composited too.
The config screen's voice face icons (CONF_PARTS child 12, 20 cells in 688 x 1008) were the alternative; they are 100-odd pixels and were not used.

**The crop** (`FaceIcon.Crops`): her eyes are the only saturated red in the face layer (`IsEyeRed`: alpha > 16, R > 150, G < 90, B < 90, R - max(G, B) > 90; the blonde
hair fails on G, the skin on all three). The box of those pixels is **(618, 581) 319 x 136** on the user's file (4385 pixels; both irises, outer corner to outer corner): the
square's side is 1.85 x that span (**590 px**) for 48 px and up and 1.45 x (**463 px**) for 16..32, centred on the eyes horizontally with the eye line at 40 % of the height.
The square is cut out of body + face (only the tiles that touch it are decoded; the whole build took **155 ms** in the game's hidden run, 35 ms of it the crops and 109 ms the
seven renders in the data test) onto the launcher's night indigo (#0E1532), which no pixel of this square shows (it is all hair, face and collar). The Python prototype that
settled the numbers is `scratch/k23/icon_proto.py` (its first try, 1.55 x with the eye line at 42 %, cut the chin; `probe/icon_sheet.png` is the final arithmetic).

**The render** (`FaceIcon.Render`): every size is sampled from the full-size square on its own (supersampled bilinear: 2..32 samples per axis so each output pixel averages
the source under it; nothing is a resized copy of another size), masked to a rounded square (corner radius 20 %, the mask 4 x 4 supersampled) with a rim of the launcher's
moon-blue #8FA6FF inside the edge (1 px at 16..32, 1.5 at 48..64, 2 at 128, 3 at 256) and transparent corners. `EncodeIco` writes the seven sizes as 32-bit BMP entries (the
256 one with the Vista 0 x 0 directory entry; 372,526 bytes); `DecodeIco` reads them back.

**The pictures read** (`scratch/k23/icon/`, written by `FaceIconRealDataTests`): `icon_contact.png` (256, 128, 64, 48, 32, 24, 16 on grey), `icon_small_x4.png` (16, 24, 32, 48
enlarged four times without filtering), `icon_256.png`, `icon_16.png`, `icon_32.png`, `icon_48.png`, `crop_wide.png` (the 590 px square). Honestly:

* **256**: a clear close-up: both red eyes, the nose, the smile, the bangs and the hair on both sides, the collar at the bottom edge; the rim is a thin blue line. It reads as
  Arcueid at once.
* **48**: still a face with red eyes and a visible smile; the hair strands blur into blonde shapes. Recognisable as her to anyone who knows the sprite.
* **32**: a blonde face with two red eyes and a hint of the mouth; the rim is one clean pixel. Readable as "a blonde anime face with red eyes"; the tighter crop helps (the
  eyes are 4..5 px wide).
* **16**: a blonde head, two red dots for the eyes, a skin-coloured lower half, the blue rim. It is a face, and the red eyes say which one if you know, but no more than
  that: at 16 px no face is more than a few blobs. The crescent of K20 is a simpler shape at this size; the user asked for the face, and the title bar on a 100 % display
  gets exactly this 16 px frame (20 px at 125 %, 24 at 150 %, where the eyes and mouth come back).

**Where it is used** (all three asked for):

1. **The game window** (`GameApp.StartFaceIcon` / `ApplyFaceIcon`): once the game folder is open the build (or the cache check) runs on a worker thread, so the start never
   waits for a decode; the loop applies the result when it is ready: `GameWindow.SetIcon` with the 256 px frame (SDL, the portable path) and then, on Windows,
   `GameWindow.SetIconFile` (new: `LoadImageW(LR_LOADFROMFILE)` at `SM_CXSMICON` / `SM_CXICON` and `WM_SETICON` ICON_SMALL / ICON_BIG, the handles kept until the window
   is disposed; SDL's own icon is left to SDL), so the title bar, Alt+Tab and the taskbar take the frame drawn for their size instead of one scaled bitmap. Until then, and
   whenever the folder has no usable picture, the window keeps K20's crescent (the executable's icon group through the window class). Log lines: `face icon: built from
   ARU_A_00_00_N00.MZP (eyes at 618,581 319 x 136; squares 590 and 463 px) into <profile>\icons\tsukihime.ico in 155 ms`, `window icon: Arcueid from <path> (SDL 256 px set,
   per-size frames set)`; a cache hit logs only the second. The run's end waits for a build still in flight before the archives are unmapped (`Dispose`).
2. **The launcher window** (`LauncherModel.LoadGameIconAsync`, `MainWindow.ApplyGameIcon`, `GameIcon.Load`): after every refresh of a ready folder the same cache is ensured
   on a worker thread and the window's `Icon` takes the .ico through an `IconBitmapDecoder` (WPF picks the frames for the title bar and the taskbar); an invalid folder puts
   the crescent back. The offscreen render's `window_ok.txt` now ends with `game icon <path>`.
3. **The shortcuts**: `Shortcuts.Game(folder, exe, iconPath)` points `Tsukihime.lnk` at the cached .ico when it exists (`LauncherModel.ShortcutIcon`), else at the exe's
   crescent as before; `Tsukihime Launcher.lnk` keeps the crescent (it is the launcher's own icon). The bare `.exe` files keep the crescent too.

**The cache** (`FaceIconCache`): `<profile>\icons\tsukihime.ico` and `tsukihime.src` = `v1|ARU_A_00_00_N00.MZP|<full game folder path>`; `IsCurrent` compares the stamp (a
trailing separator or another spelling of the same folder is the same folder), so the icon is rebuilt when the folder changes or `FaceIcon.Version` is bumped, and a current
file is used without opening the game folder. The profile is `--save-dir` / `--data`, else `%APPDATA%\Tsuki`, the same place for both programs. `FaceIcon.cs` lives in
`src/Tsuki.App/Play` and is compiled into the launcher (and the Render tests) as `AppSettings.cs` is, so it uses Tsuki.Data and Tsuki.Engine only.

## 2. Text for text hookers (request B)

**2.1 One producer** (`TextFeed.cs`: `PlainText`, `ITextOutput`, `TextFeed`). K21's `TextCopier` held the detection and the plain-text rule; both moved into `TextFeed`
(the watcher: a message that started or grew, a choice list that opened, the `@n` continuation yielding only the added tail, never the same text twice in a row, and the
"every switch off: follow the page silently" rule, now over all outputs) and `PlainText` (`Message`: `Markup.PlainText` with the ruby dropped and `^` joined by a space in
English and nothing in ja / zc / zt; `Choices`: one line per non-empty choice as shown, number prefix included; `WithName`: the speaker's plate above the text,
`name\ntext`). The speaker name: Tsukihime's text is NVL and the PS4's name plate writers have no callers (`GameHost.NamePlate`: empty in every retail run), so the plate
appears above a line only when the game shows one; a continuation tail never repeats it. `TextCopier` is now the clipboard output (`ITextOutput`: `Name`, `Enabled`,
`Tick`, `Send`), unchanged in what it writes and logs (`clipboard: message, N chars`, the toast once per run, `--clipboard-file`).

**2.2 The hook point** (`TextHookOutput.cs`, `Tsuki.Platform/GdiTextHook.cs`): each produced line goes once through **`ExtTextOutW`, `TextOutW` and `GetTextExtentPoint32W`**
on a memory DC (`CreateCompatibleDC(NULL)`, deleted after the call; nothing is drawn anywhere, the three calls take microseconds). Why these: Textractor's
`texthook/engine/native/pchooks.cc` (fetched during this package, `scratch/k23/textractor_pchooks.cc`) installs its default GDI hooks in `PcHooks::hookGDIFunctions` on
gdi32's `GetTextExtentPoint32A/W`, `GetTextExtentExPointA/W`, `GetCharacterPlacementA/W`, `GetGlyphIndicesA/W`, `GetGlyphOutlineA/W`, `ExtTextOutA/W`, `TextOutA/W`,
`GetCharABCWidths*`, `GetCharWidth*` and user32's `DrawText(Ex)A/W`, `TabbedTextOutA/W`; LunaHook is a fork of Textractor with the same hook set (its own `pchooks.cc` could
not be fetched here: both raw and blob URLs of its repository returned 404 from this machine). The three chosen are the plain string-drawing and string-measuring calls
(`DrawTextW` would add a fourth thread with the same text; `GetGlyphOutlineW` is per character). **Config > System > Text Hooker Output**, On by default; settings.ini
`text_hooker=`. Log `hooker: message|choice, N chars`, the state line `hooked N`. The sink is an interface (`ITextHookSink`), so the tests see the calls without GDI; the
real sink's calls are checked to return TRUE on Windows. **Not run with LunaHook or Textractor** (nobody at the keyboard; a hooker would have to be installed and attached by
hand): the steps for the user are in README ("Text hookers and dictionaries") and below.

**2.3 The WebSocket** (`TextWebSocket.cs`): `TextWebSocketServer` is a minimal RFC 6455 server on a `TcpListener` bound to **127.0.0.1 only** (no HttpListener, no URL
reservation, so no firewall prompt): the HTTP upgrade is parsed (GET, `Upgrade: websocket`, `Connection: Upgrade`, `Sec-WebSocket-Key`; anything else gets 400),
`Sec-WebSocket-Accept` is SHA-1 of key + GUID, each text is one unmasked FIN text frame (7-, 16- or 64-bit length) to every client through a per-client channel and writer
task (a client that stops reading is dropped after 5 s), a client that connects late receives the latest text first, client frames are read and unmasked (close is answered
with its code, ping gets a pong, data is ignored). `TextWebSocketOutput` starts the server when the switch goes on (`Tick`, on the game thread), stops it when it goes off,
reports a port in use once (toast `The text WebSocket could not start on port {0}: {1}`, not retried until the switch is toggled) and shows `Text WebSocket: ws://127.0.0.1:{0}`
when listening. **Config > System > Text WebSocket**, Off by default; settings.ini `text_websocket=on|off`, `text_websocket_port=` (default 6677, texthooker-ui's default
address). Plain text frames: compatible with texthooker-ui and any page that appends what it receives. Log `websocket: listening on ws://127.0.0.1:P`, `client connected (N
connected)`, `client left`, `message, N chars to C clients`, `stopped`; the state line `websocket off | port P (C clients) | port P failed, sent N`.

**2.4 The rows**: `PortRow.TextHooker`, `PortRow.TextWebSocket` (`CtlKind.TextHooker`, `CtlKind.TextWebSocket`) between Copy Text to Clipboard and Text Window Opacity in the
System tab's band, which is now six rows (`BandFor(6)` = 384; the tab scrolls 750 + 384); `ConfigScreen.SwitchKind` / `IsSwitch` name the Off / On pill rows. Headings:
ja テキストフッカー出力 / テキスト WebSocket, en Text Hooker^Output / Text WebSocket, zc 文本钩子输出 / 文本 WebSocket, zt 文字鉤子輸出 / 文字 WebSocket (the glyph pages of
every language draw them: `PromptRealDataTests`). `IUiPortSettings.TextHookerOutput` / `TextWebSocket`, `PreviewPortSettings` (hooker on by default), `PortSettings` (both,
plus the read-only `TextWebSocketPort`), `AppSettingsData.TextHooker` / `TextWebSocket` / `TextWebSocketPort`. Two `PortText` entries (`TextWebSocketListening`,
`TextWebSocketFailed`) in the four languages. Renders read: `scratch/k23/ui/ui_config-port_{ja,en,zc,zt}.png` and `band_*_crop.png`: the six rows with their headings at the
sheet's label x, the English two-line headings apart from their neighbours, no overlap with the pills.

**For the user, step by step** (also in README):

* LunaHook / LunaTranslator or Textractor: start `Tsukihime.exe` (or PLAY), attach the hooker to the process `Tsukihime.exe`, advance one line, pick the thread named
  `ExtTextOutW` (or `TextOutW` / `GetTextExtentPoint32W`; all carry the same whole line, once, when it starts displaying). No H-code. Config > System > Text Hooker Output
  turns it off.
* texthooker-ui (Yomitan): Config > System > Text WebSocket On (or `text_websocket=on`), open the page, let it connect to `ws://127.0.0.1:6677`; change the port in
  `settings.ini` if 6677 is taken (the toast says so).
* Clipboard watchers: Config > System > Copy Text to Clipboard, as in K21.

## 5. PS4 versus Switch

Nothing new: the icon and the three text outputs are the port's own. knife has a `--text-websocket HOST:PORT` option (`text_stream.rs`, read for behaviour: every message and
choice list as one plain-text message, the latest text to a late client); ours follows the same contract from its own code, is on 127.0.0.1 only and is a config row.

## 6. Open issues

1. **Not tried with a real hooker.** LunaHook / LunaTranslator and Textractor were not installed or attached here (nobody at the keyboard). The calls are the ones their
   default GDI hooks intercept per Textractor's `pchooks.cc`; whether the hooker lists the thread as `ExtTextOutW` or shows the user32 names first, and whether it needs the
   64-bit build (Tsukihime.exe is x64: use LunaHook's / Textractor's x64 host) is for the user to see. README says what to pick.
2. **No visible check of the title bar and the taskbar.** The per-size frames are proven by `LoadImage` and `WM_SETICON` returning success on a real window and by the
   launcher's offscreen window taking the .ico; what the 16 / 20 / 24 px frame looks like in a real title bar at the user's DPI was judged from the PNGs only (section 1).
3. **The crop is tuned for one sprite.** `ARU_A_00_00_N00` is the fixed source; the eye search is a safety net (no red box, or one that is not two eyes side by side, keeps
   the crescent), not a general face finder. A different expression (the half-closed eyes of N02..N05) would move the box; the version stamp allows a change of mind.
4. At 16 px the face is a blonde head with two red dots (section 1). If the lead prefers the crescent at the small sizes, `FaceIcon.RenderAll` could take K20's frames for
   16 and 24 from the embedded picture; not done, the user asked for the face.
5. The icon of a skipping run's first frames is the crescent for a moment (the build runs beside the start; 155 ms on this machine on a cache miss, a file read on a hit).
6. The hooker output passes a line once when it starts displaying, as the clipboard does; a hooker expecting the typewriter reveal sees whole lines early. The three APIs
   each carry the text, so the hooker shows three threads with the same lines: the user picks one.
7. The WebSocket frame is plain text (texthooker-ui's contract). Tools that want JSON (`{"text": ...}`) are not served; a second frame format would be a settings key.
8. `text_websocket_port` has no config row (the file only), as asked.
9. The speaker's plate above the text is `name\ntext`; retail never shows a plate, so no retail line changes. If a future script fills it, a hooker sees two lines.
10. The three fetched reference files (`scratch/k23/textractor_*.cc`) are Textractor's source under its licence, kept in `scratch/` for the record only.
