# K10: crash fix (quit while a clip decodes), second shutdown defect (hang), test hardening

Package K10 of the knife-reference wave, run on 2026-10-26 on top of commit 266e739. Nothing is committed. Every number below comes from a command run in this session.
All runs used a **hidden** SDL window, `--mute` and `SDL_AUDIO_DRIVER=dummy` (no sound was played); `artifacts/play` and `%APPDATA%\Tsuki` were never touched (every run used `--save-dir scratch\K10\...`,
builds went to `artifacts\K10`, `artifacts\K10old`); the game folder was only read; shadPS4 was not started.

## 1. Result

| item | state |
|---|---|
| cause of the Windows event 1026 crash (`Atrac9Decoder.DecodeAll` on a pool thread) | **found**: `GameApp.Dispose` unmapped the archives (`GameFolderSource.Dispose`) while clip decodes were still reading them; a read of an unmapped page is an access violation, which .NET cannot catch |
| fix | shutdown order + a lease on the mappings: the source waits for the decodes that read it, the clip cache and the player stop decoding first, the warm-up thread is joined |

## 2. Evidence

**The user's machine** (`Get-WinEvent -FilterHashtable @{LogName='Application'; Id=1026}`): four events, 15:52:48, 15:53:45, 15:53:54, 15:54:22, `Tsuki.App.exe`, ".NET Version 10.0.13", "The process was terminated due to an
unhandled exception", **no `Exception Info` line** (there is no managed exception object: the runtime logged a fatal hardware fault), managed stack `Atrac9Decoder.DecodeAll <- Lazy<T>.ViaFactory <- CreateValue <- ClipCache.Get <- thread-pool
worker`. The user's build is `artifacts/play` (built 14:29 from 83d6842); the code involved is the same at HEAD.

**The same event on this machine** (event 1026 at 16:29:38, identical text and stack) came from the first reproduction: K8's own command (`--hidden --mute --fast --autoplay skip --choices first --shot-at 300,600,...,12000`), which printed
(redirected stderr)

```text
Fatal error.
0xC0000005
   at Tsuki.Media.Audio.Atrac9Decoder.DecodeAll(Tsuki.Media.Audio.RiffAtrac9, System.ReadOnlySpan`1<Byte>)
   at System.Lazy`1[...].ViaFactory(...)   ... ClipCache.Get ... ThreadPoolWorkQueue.Dispatch()
```

**after** the log line `done: 12100 steps` (the run had finished; the crash came while `GameApp.Dispose` ran). Bash reports an access violation as exit 139: that is the code K8 saw ("segmentation fault at the end of a long hidden
run", K8.md 10 item 6). It is a quit-time fault, not a long-run fault: it also happens after 1,500 steps.

**Deterministic reproduction without the game loop** (`scratch/K10/repro`, `Program.cs`; 40 BGM prefetches through `ClipCache` over `GameFolderSource.Audio`, 30 ms later `GameFolderSource.Dispose()`, as `GameApp.Dispose` does):

```text
[ 14] decode begin Bgm#8 payload 4055208 bytes        (16 clips in flight)
disposing the source with 16 decodes in flight
Fatal error.
0xC0000005
   at FFmpeg.AutoGen.DynamicallyLoadedBindings+<>c.<Initialize>b__2_523(AVCodecContext*, AVPacket*)
   at FFmpeg.AutoGen.ffmpeg.avcodec_send_packet(AVCodecContext*, AVPacket*)
   at Tsuki.Media.Audio.Atrac9Decoder.Decode(ReadOnlySpan`1<Byte>, Int32, Int32, Span`1<Single>)
   at Tsuki.Media.Audio.Atrac9Decoder.DecodeAll(...)  <- MediaAudioDecoder.Decode <- GameFolderSource.Audio <- ... <- ClipCache.Get <- ThreadPoolWorkQueue.Dispatch()
```

5 of 5 runs crashed (exit 139, `scratch/K10/repro_race1..5.txt`); with the decodes drained first (control) the process survives. The faulting native call is `avcodec_send_packet`: the packet is not reference-counted
(`Atrac9Decoder.Decode` points `_pkt->data` into the payload), so libavcodec copies `BlockAlign` bytes from `p + DataOffset + s * BlockAlign`, a pointer into the memory-mapped archive that `MappedFile.Dispose` has just unmapped.
The Windows stack shows `DecodeAll` on top because the P/Invoke frames are folded into their managed caller.

Why E1's test never saw it: it decoded all 17,925 streams but never disposed the source while decoding.
Dumps: `DOTNET_DbgEnableMiniDump=1` / `DbgMiniDumpType=2` writes a dump in the harness but only a truncated, unreadable one in the app (the process dies first: "did not contain a system info stream"); the harness stack above is the
faulting frame. `dotnet-dump` 10.0.750501 was installed as a local tool in `scratch/K10/tools` and used for the hang in section 4.

**Ruled out**

* A bad stream: 1,349 streams of real entries with noise or 40 flipped bits in the superframes (header intact; `Repro fuzz`, 3 seeds) were all rejected as `InvalidDataException` ("avcodec_send_packet failed"), none crashed; the same check is now a test.
* A write past `dst` in `Atrac9Decoder.Drain`: the capacity check `baseIndex + n * ch > capacitySamples` precedes every write, `Finish` uses the same check; no write beyond the output was found.
  What was missing is the **input** bound: `Decode` trusted the header, so a header from another stream (or a stream cut short) would have read past the span. Added (section 3).
* The HE-VAG path (`HeVag.cs`): fully managed, every index is bounds-checked, no pointer; it cannot fault the process.
* The prefetch/eviction logic: no memory unsafety, but a flaw found by the new test: `Evict` stopped at the clip it keeps even when that clip was the oldest *request*, leaving every later clip resident above the budget. Fixed (section 3).
* Concurrent FFmpeg load: `FfmpegLibrary.Load` is under a lock and `IsLoaded` is set last.

## 3. Fix

| file | change |
|---|---|
| `src/Tsuki.Data/Containers/UseGate.cs` (new) | counts the threads that read a resource through raw pointers; `Close(timeout)` refuses new ones and waits for those inside (increment-then-check against flag-then-count, both full fences) |
| `src/Tsuki.Data/GameFolderSource.cs` | `Audio`, `Picture(int,int)`, `UiSheet`, `UiSheetSize`, `UiSheetLayout`, `Parts`, `Script`, `FontPage` hold a lease; `Dispose` marks the source, closes the gate (15 s) and unmaps only when no decode is left (otherwise the mappings stay until process exit instead of being pulled away); `_disposed` is volatile |
| `src/Tsuki.Media/Sound/ClipCache.cs` | `IDisposable`, `Shutdown(timeout)`: the decode function runs inside a gate; after the shutdown `Get` throws `ObjectDisposedException`, `Prefetch` does nothing; `Evict` skips the kept clip instead of stopping at it |
| `src/Tsuki.Media/Sound/AudioCommandPlayer.cs` | `IDisposable`, `Shutdown(timeout)` = the cache's |
| `src/Tsuki.App/Play/GameApp.cs` | `Dispose` order: stop and join the warm-up thread (it checks a stop flag per step), feeder, movies, output, pads, **`_player.Shutdown`**, cache, compositor, then the source (skipped, with a log line, if a thread did not stop in 10 s); audio failures are written to the log as they happen (`audio failure Voice#13: InvalidDataException: ...`) |
| `src/Tsuki.Media/Audio/Atrac9Decoder.cs` | `Decode` checks `DataOffset + (first + count) * BlockAlign <= stream.Length` before any pointer arithmetic (`ArgumentException`), and `first + count` in 64 bits |
| `src/Tsuki.Render/Textures/StagingPool.cs` | section 4 |

A decode error never ends the process: a managed failure (`InvalidDataException`, `ArgumentException`, `ObjectDisposedException` after the shutdown, ...) is thrown inside the `Lazy` factory, forgotten by `ClipCache.Get`, swallowed by a speculative `Prefetch`, and for a play
becomes a faulted task that `AudioCommandPlayer.Pump` turns into an `AudioPlayFailure` (the stream is silent, `IsPlaying` is false, the next play works) and a log line. There is no catch of an access violation anywhere.
A native fault inside libavcodec cannot be caught in-process; the only protection is not handing it bad pointers, which the lease and the input bound do.

## 4. Second defect: the process did not exit after the last frame

A 100,000-step `--fast` soak (`done: 100000 steps in 78.5 s`) never ended: 17 threads, 8.5 GB working set, no progress for 10 minutes. `dotnet-dump collect --type Mini` + `clrstack -all`
(`scratch/K10/hang_stacks.txt`): the main thread in `GameApp.Dispose -> TextureFeeder.Dispose -> DecodeWorkers.Dispose -> CancellationTokenSource.Cancel -> StagingPool.Rent.<callback>` waiting for `Monitor.Enter(_gate)`; a
decode worker in `StagingPool.Rent` line 115, **disposing its cancellation registration while still holding `_gate`**, which waits for the callback the main thread is running, which needs `_gate`. A deadlock between `Cancel` and a woken renter.
It is in the old build too (a 4.4 s run, `ab_old_4500`, same stack, source path `scratch/K10/old/...`); 3 of 10 short runs of the old build hang this way.

Fix: `Rent` registers the wake-up callback once (static callback, only when it has to wait) and disposes the registration after leaving the lock (`try/finally`); after registering it looks again before waiting (a `Cancel` that races with `Register` runs the callback inline and its pulse would be lost).
Proof: `scratch/K10/stagerepro_*` (300 rounds x 6 waiters, then `Cancel`): the HEAD `StagingPool` hangs (killed by `timeout 120`), the fixed one finishes 300 of 300; test `StagingPoolCancelTests` (200 rounds, `Cancel` on a thread of its own so a hang fails instead of hanging).

## 6. `MovieOpenTests.OpeningAMovieReturnsAtOnceAndTheSlotReportsAMovieThatIsNotOverUntilThePlayerIsReady`

It failed once in the full parallel Data run and passes alone. The assertion was `openMs < 100` for one `Perform(Open)`: in the full run every core is busy and the scheduler can park the calling thread for longer than the open takes (about 79 ms at idle; a call that did the
open itself would also be under 100 ms alone, so the bound barely discriminated). Now: up to six attempts on fresh slots; an attempt passes when the call returned within 100 ms **and** `IsOpening(slot)` is true right after it (the open is still running on its worker: the structural fact the test is about);
a stall has to hit all six to fail, and everything after (clock not over, player appears, no failure, closing a pending open) is unchanged. It passed in all five full Data runs.

## 7. Other test changes (needed for a clean full run)

* `LoadingTests` and `TextureFeederTests` (K8) failed once (`SDL_GL_SetAttribute: Video subsystem has not been initialized`): `SDL_InitSubSystem` / `QuitSubSystem` are not thread-safe and the two classes create and dispose windows at the same time. Both are now in the collection `SdlWindowCollection`
  (new, `tests/Tsuki.Tests.Data/App/SdlWindowCollection.cs`): sequential among themselves, still parallel with the other tests.
* `LoadingTests.TheScriptsAScriptJumpsToAreDecodedOnAWorkerWhenItIsFirstUsed` failed once with "no jump target was decoded ahead": `ScriptCache` prefetches on the thread pool, which the full parallel run keeps busy; the test waited 10 s, it now waits 60 s (the app's pool is not starved).
* My own Data tests run their clip requests on threads of their own, not the pool, for the same reason (first draft failed with "the decodes never started" in the full run).

## 9. Open issues

1. **Not observed in the user's session**: the four events have the stack of the quit-time fault, and every reproduction of that stack came from `Dispose` with decodes in flight, but nothing in the event log says when in their session the process died. If a crash with this stack happens while playing (not at quit) it is
   a new case: soak runs of 160,000 steps found none.
2. The real SDL audio device path was not exercised (no sound allowed); the muted runs pull the mixer and decode the same clips.
3. Other readers of the mappings are protected by order, not by a lease: `DecodeWorkers` (joined by `TextureFeeder.Dispose` first, which could hang before section 4), `ImageMzp` windows from `OpenImage` / `OpenUiSheetImage` (valid until the source is disposed, documented). A new background reader must be joined
   before the source is disposed or hold a lease. `GameFolderSource.Dispose` leaves the mappings in place if a lease is still held after 15 s.
4. Working set: 3.2 GB in the middle of the paced soak, 8.5 GB in the hung fast run after 100,000 steps (296,219 tiles decoded, 1.5 GB of textures resident, 64 MB staging). Not investigated; it did not grow without bound in the 100,000-step run that finished.
5. A clip whose decode fails is retried at every request (the failure is not cached on purpose, a transient `ObjectDisposedException` must not stick) and appended to `Failures` each time.
6. `DOTNET_DbgEnableMiniDump` cannot capture this crash in the app (truncated dump); use the harness (`scratch/K10/repro`) or run the app under a debugger.
