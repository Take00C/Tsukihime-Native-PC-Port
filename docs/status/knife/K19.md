# K19: windowed mode that is a window, and Display Mode / Window Size in the game's Config

Package K19 ("display"), run on 2026-10-30 on top of commit 38cc3af (K18). The user's report: with Fullscreen OFF in the launcher the game still opens fullscreen (or looks
fullscreen), and the game's own Config has no fullscreen / windowed option. Nothing is committed. Builds in `artifacts/display` (Release, `-warnaserror`), temporary profiles under
`scratch/display/`, hidden and muted runs except the three visible checks of section 4 (this agent was allowed a visible window; each ran a few seconds, muted, and exited by
`--exit-after`). `artifacts/play*`, `artifacts/dist`, the user's `%APPDATA%\Tsuki` (read for the diagnosis, never written) and the game folder (read-only) were not touched.

## 1. The root cause, end to end

**What the user's machine holds** (read-only): `%APPDATA%\Tsuki\settings.ini` has `window=2560x1440` (the launcher's largest preset, chosen on the Display page) and the one monitor is
2560 x 1440 with a work area of 2560 x 1392 (`[System.Windows.Forms.Screen]::AllScreens`: `bounds={X=0,Y=0,Width=2560,Height=1440} work={X=0,Y=0,Width=2560,Height=1392}`).
`last_run.log` ends with `window mode: fullscreen (command line, remembered)`, so the K18 byte path itself worked on the last PLAY.

**What the K18 code did with that** (`src/Tsuki.Platform/WindowPlacement.cs` at 38cc3af, lines 49..76): `SDL_SetWindowSize(2560, 1440)` and then
`SDL_SetWindowPosition(display.X + max(0, (2560 - 2560) / 2), display.Y + max(0, (1440 - 1440) / 2))` = the client area at (0, 0), as big as the monitor; SDL window positions are client
positions, so the title bar sat above the top edge of the screen. The window *was* a window (`WS_CAPTION`, `WS_THICKFRAME`), it only could not be told from fullscreen.

**Reproduced visibly with the K18 build** (`scratch/display/capture.ps1`, `scratch/display/vis_before/report.json`, `screen.png`): `Tsuki.App.exe --windowed --mute` with a temp profile holding
`window=2560x1440`: `clientSize 2560 x 1440`, `clientOrigin 0,0`, window rect `-8,-31 - 2568,1448`, DWM frame `-1,-31 - 2561,1441`, `hasCaption true`, `titleBarOnScreen false`,
`frameInsideWorkArea false`, `clientCoversMonitor true`; the log said `window mode: windowed (command line, remembered)`. The screen capture shows the boot notice edge to edge, no title
bar, no task bar.

So K18's suspicion (section 1 of K18.md) was right: the window-size preset, not the mode. Two smaller things went with it: the default windowed size was 1280 x 720 and the window was
created at the file's size *before* being moved, so it flashed up wherever Windows put it.

## 2. What changed

### The window (Tsuki.Platform, Tsuki.App)

* `WindowFit` (new, `src/Tsuki.Platform/WindowFit.cs`, no SDL; compiled into the launcher by a file link like `AppSettings.cs`): the presets (1280 x 720, 1600 x 900, 1920 x 1080,
  2560 x 1440), the share of the work area a window may take (**90 %** of its width and of its height), `Clamp` (a size that does not fit is scaled down keeping its own aspect ratio, even
  width), `Largest` (the largest 16:9 size that fits), `Default` (**1600 x 900**, else `Largest`), `PresetsFor` (the presets that fit), `Centre`. On the user's monitor: 2560 x 1440 ->
  **2224 x 1251** at (168, 70); the presets offered are the first three.
* `WindowPlacement.Place` now always sizes and centres: the display is the one of `monitor=` else the window's own; the size is the file's else the window's; it is clamped to the display's
  **work area** (`SDL_GetDisplayUsableBounds`, the desktop less the task bar) and the client area is centred in that work area; the window's minimum size is 640 x 360. It returns a
  `Placement` (display, matched, size, position, clamped) that the game logs: `window: 2224 x 1251 at (168, 70) on "..." 2560 x 1440 (work area 2560 x 1392 at (0, 0)), clamped to the
  work area (settings asked for 2560 x 1440)`. `WindowPlacement.Resize`, `DisplayOf`, `WindowSize`; `DisplayInfo` carries the work area; `GameWindow.WindowSize`, `IsMaximized`.
* `StartupSettings.WindowOptions()` creates the window **hidden** at the requested size (default 1600 x 900); `GameApp.Play` places it, logs the placement, shows it, and only then asks
  for `--fullscreen` (borderless fullscreen takes the display the window is on, so the K17 "fullscreen after placing" special case is gone). Fullscreen is `SDL_SetWindowFullscreen` with
  no display mode = borderless on the window's monitor, as before.
* `DisplaySettings` (new, `src/Tsuki.App/Services/DisplaySettings.cs`, `IUiDisplaySettings` over an `IDisplayWindow`; `SdlDisplayWindow` is the game window, a fake is the tests'):
  `Fullscreen` reads the window's requested state and sets it (switch + the config block byte 0xA9 + commit, so the launcher's switch reads it); `WindowSize` leaves fullscreen,
  resizes through `WindowPlacement.Resize` (clamped, centred) and writes `window=WxH` into settings.ini at once (always: an explicit choice is persisted even when it is the size the
  run started with); `SizeChoices` = the presets that fit the work area of the window's
  monitor; `NoteFullscreen` is the Alt+Enter / F11 path (the pump switches, the state is remembered the same way, so the row and the keys cannot disagree); `NoteResized` keeps the size of a
  window that is neither fullscreen nor maximized (a drag), and `SaveWindowSize` writes it at exit when it is not the size the run started with (a clamped file value is **not**
  written back by itself: the file keeps the user's value until the user changes the size).
* `GameApp`: `FullscreenToggled` and `PixelSizeChanged` go to the display settings; `SaveWindowSize` before the final commit; `AppServices.Display` hands the settings to the UI. Hidden
  verification runs have them too (the rows exist there; a hidden window never shows fullscreen but stores the choice, as K18's did).

### The Config screen (Tsuki.Ui)

* `IUiDisplaySettings` (`IGameServices.cs`) and `IUiSystemServices.Display` (default null: a game without a window shows no rows); `PreviewDisplaySettings` for the previews and the tests.
* `ConfigScreen`, System tab: two new control kinds, `Display` (0 Windowed, 1 Fullscreen) and `WindowSize` (one pill per preset that fits), drawn with the same `UiPrompts.DrawPill`
  as the Controls tab's Button Prompts row, headings with `UiPrompts.DrawText` at the sheet's own label x (431, "Language" starts at sheet x 45). They sit in a band added under the
  language row: the System page sheet (1432 x 1602) is drawn in three pieces (rows 0..1500; rows 1400..1500, a flat part of the band below the "Language" label, stretched into the
  extra 160 px; rows 1500..1602, the band's bottom edge, moved down) with the sheet's own group rule (row 1310) copied above the rows. The tab scrolls 910 px instead of 750.
  Cursor grid: the two rows follow the four language rows (Down from 繁體中文 lands on Windowed; Left / Right along a row; Up from the mode row returns to the languages); the pointer hovers
  and clicks the pills; the wheel, the page keys and the scroll bar reach them. Decide on a mode pill applies it at once (the game switches and remembers); a size pill resizes the
  window (and leaves fullscreen first). In fullscreen the size row is drawn at half alpha with the remembered size still marked: it is the size a return to the window gives, and choosing a
  size there is the way back to a window. `CursorTo` (internal) for the tools and the tests. Labels: ja 画面モード ウィンドウ / フルスクリーン, ウィンドウサイズ; en Display Mode
  Windowed / Fullscreen, Window Size; zc 显示模式 窗口 / 全屏, 窗口大小; zt 顯示模式 視窗 / 全螢幕, 視窗大小; sizes "1280x720" in the English pages everywhere.
* `UiPreview` scenes `config-display` (System tab scrolled to the rows, cursor on Windowed) and `config-display-full` (fullscreen, cursor on Fullscreen) for `ui-shot` and the real-data tests.

### The launcher

* `MonitorEntry` carries the work area (`MONITORINFOEX.rcWork`); `LauncherProfile.WindowSize` defaults to 1600 x 900 and `EffectiveWindowSize(workArea)` is the clamp; the status line shows
  the effective size (`2224 × 1251 · Windowed` for the user's file on the user's monitor).
* Display page: the window-size control lists `WindowSizes` (the presets that fit the chosen monitor; `WindowSizeChoice`, value equality so the selection finds its item), `SelectedWindowSize`
  (null for a size that is none of them: a dragged size, or a file value too big for the monitor), and `WindowSizeNote` ("The game opens as a 2224 × 1251 window on Display 1 (settings.ini
  asks for 2560 × 1440, which does not fit). It stays inside the monitor's work area, at most 90 % of it, and remembers a size you drag it to."). The Fullscreen row's text names the
  in-game row. `WindowSizeIndex` / `SizePresets` are gone (the `--selftest` uses the new members). `KeyTable`: "Alt+Enter / F11: Fullscreen on / off (the same as Config › System › Display
  Mode)" (Controls and Help pages).

### Documents

`README.md` (Window bullet, `window=` row, the input table's Alt+Enter / F11 row, the launcher's Display line); this file.

## 5. Open issues

1. Not tried by hand (nobody at the keyboard): dragging the window's edge (the `PixelSizeChanged` path is unit-tested over the fake window and the size events of the real window were
   seen at start), Alt+Enter in the visible window (the pump path is K18's, tested in `PlatformSmokeTests` and through `NoteFullscreen`), a second monitor (`monitor=` matching is K17's,
   the work area of a second display goes through the same `DisplayInfo`), a pad on the new rows (they are ordinary grid controls like the Button Prompts row, which K9 drove with a pad in
   the synthetic tests).
2. The size row shows the presets that fit the monitor the window is on; on a monitor smaller than 1280 x 720 x 1 / 0.9 (a 1366 x 768 laptop) it is empty and only the mode row remains
   (the window is still placed at the largest 16:9 size that fits, 1164 x 655 there).
3. The hidden verification window (1280 x 720, not resizable) keeps the rows: its size pills show 1280 x 720 as the current size, and a choice resizes a window nobody sees. Harmless; it is
   what the real-program tests use.
4. The launcher shows no preset selected for a size that is none of them (a dragged size, or `window=2560x1440` on this monitor); the note under the control says what the game opens with.
   The file keeps the user's value until the game writes a new one (a choice in the Config, or a drag), by design.
5. The band under the System page is the sheet's own flat band stretched by 1.6; at this height the stretch is invisible in the four languages' pictures, and the test that draws the scenes
   checks textures, not pixels.
