## 1. The review (git diff against 1eb9775: 57 changed files, 40 new ones)

Read in full: every new file (`FaceIcon.cs`, `TextFeed.cs`, `TextHookOutput.cs`, `TextWebSocket.cs`, `GdiTextHook.cs`, `Shortcuts.cs`, `AppIdentity.cs`, `PortSettings.cs`,
`Screenshots.cs`, `TextCopier.cs`, `Clipboard.cs`, `PortText.cs`, `UiDialogButtons.cs`, `UiToast.cs`, `GameTitles.cs`, `ParamSfo.cs`) and the whole diff of the changed
ones (`GameApp.cs`, `AppRuntime.cs`, `GameWindow.cs`, `EventPump.cs`, `FolderDialog.cs`, `AudioMixer.cs`, `GpuCompositor.cs`, `ConfigScreen.cs`, `UiRoot.cs`, `UiPrompts.cs`,
the launcher's model, window, render and project files, the tests, README, THIRD_PARTY).

**Fixed here (small, tested):**

1. `GameApp.Dispose` waited for the icon build with `Task.Wait(ShutdownWait)`, which throws `AggregateException` when the task faulted. `FaceIconCache.Ensure` catches the
   expected exceptions, but a run that fails between `StartFaceIcon` and the first loop pass (a media or game start-up failure) disposes the app before `ApplyFaceIcon` could
   consume a faulted task, and the exception out of `Dispose` would replace the real one. Now `GameApp.WaitQuietly(task, timeout)` (a faulted or cancelled task counts as
   finished, a running one returns false as before). Test: `FaceIconTests.TheShutdownWaitForTheIconBuildNeverThrows` (faulted, completed, cancelled, still running).
2. `PortFeaturesAppTests.TheTextWebSocketServesEachLineToAConnectedPageWhenItIsOn` reused one `ClientWebSocket` across its connect retries; .NET aborts a `ClientWebSocket`
   whose connect failed, so the second attempt threw `ObjectDisposedException` (not in the catch filter). The test only passed when the very first attempt succeeded, which it
   did on K23's idle machine and did not here (the game started under a concurrent build and autoplay: `scratch/k22/test_data.log`). Every attempt now takes a fresh client.

**Looked at and left as they are** (judged not bugs, or not worth a change without the lead): `TextWebSocketOutput.Send` returns false while the switch is on but the port
could not be bound, so the feed logs `websocket: the message text could not be delivered` once per line until the switch is toggled (log noise only; the toast already said
why; no such line in any run here). `TextWebSocketServer.Dispose` disposes its `CancellationTokenSource` right after cancelling; every task that touches the token does so
inside a try that catches `ObjectDisposedException`. The game and the launcher can build the icon at the same time (PLAY right after a folder change): both write
`tsukihime.ico.tmp` and the loser logs `face icon: not built (IOException ...)` and keeps the crescent for that run. The Japanese Sound-tab heading バックグラウンドで消音 ends
right at the Off pill's left edge (no overlap; `ui_config-sound-port_ja.png`). The window title in English is the user's file's plain `TITLE`, "TSUKIHIME A piece of blue glass
moon" (no dashes: that is what the file says; the dashed form is the fallback for a file without one).

**No game art is committed or embedded.** The only binaries in the diff and the untracked set are `assets/icon/tsukihime.ico`, `tsukihime_{16,32,48,256}.png` and
`tsukihime_64.rgba`; all six were rendered to `scratch/k22/committed_icon_assets.png` and read: the crescent on the indigo plate with the sparkle, at every size.
`tools/setup/make_icon.py` imports only Pillow, argparse, struct and pathlib (no game path). The only embedded resources are the 64 px crescent (`Tsuki.App.Icon64.rgba`, 16,384
bytes = 64 x 64 x 4) and the launcher's `Assets\tsukihime.ico`. The icon groups of the built and the published `Tsukihime.exe` and `TsukihimeLauncher.exe` were extracted by
parsing the PE resource directory in Python (`pe_icon.py`, no Win32 calls): 10 entries each (16..256 px, 32 bpp), **byte-identical to `assets/icon/tsukihime.ico`, 10 of 10**;
`scratch/k22/pub_icons/game_icon.png` and `launcher_icon.png` read: the crescent. The Arcueid icon exists only in the profile folders of the runs (`scratch/k22/*/save/icons/`).

## 3. Open issues

1. Not tried with a real hooker (LunaHook / Textractor) or a real texthooker-ui page: the GDI calls and the WebSocket were checked by their return values, the log counts and a
   raw client; K23's open issue 1 stands. The hook point's "per line" is per produced line (a message, its `@n` tail, a choice list), as designed.
2. No visible window was shown: the title bar / taskbar look of the Arcueid frames and of the Japanese caption was judged from the PNGs and the logs (K20 open issue 3, K23
   open issue 2 stand).
3. `TextWebSocketOutput` logs a "could not be delivered" line per message while its port is taken (section 1); harmless, left for the lead to decide.
4. The launcher's `--render` sidebar shows the drawn crescent (the Shell's own art); the window icon is reported by `window_ok.txt` only.
