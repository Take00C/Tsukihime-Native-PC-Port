# K18: window mode that the launcher decides, the title's idle fade-out, EXIT on the title

Package K18, run on 2026-10-27 on top of commit 007832c. Three things the user found in the published build (`artifacts/dist`). Nothing is committed. Every check used hidden windows,
`--mute`, `SDL_AUDIO_DRIVER=dummy`, temporary save folders (`scratch/K18/save*`), builds in `artifacts/K18` (publish: `artifacts/K18pub`) at below-normal priority.
`artifacts/play*`, `artifacts/dist`, the user's `%APPDATA%\Tsuki` and the game folder (read-only) were not touched. Result for the lead to look at: `artifacts/dist_k18/Tsuki`
(`TsukiLauncher.exe` + `Tsuki.App.exe`, 276 MB, `dotnet publish src/Tsuki.Launcher -c Release -r win-x64 --self-contained -p:PublishReadyToRun=true`).

## 1. The game started fullscreen with Fullscreen OFF in the launcher

**What the K17 flow did.** The launcher's switch wrote a one-shot `fullscreen=on|off` line into `settings.ini`; the game applied it to the window-mode byte of the config block
(0xA9) at start and removed the line; with no line the game used the byte that Alt+Enter / F11 had left, and the switch showed `line ?? byte`. So what the game did depended on
whether a line was still there, on the byte of the last run and on the byte being saved; `--fullscreen` on the command line neither read nor stored the byte.

**What I could not do:** reproduce "OFF but fullscreen" in a hidden window (a hidden window never goes fullscreen; the byte path is what the tests and the hidden run check). One more cause
is possible and is **not** changed here (not asked): the launcher's window-size presets include 1920 x 1080 and 2560 x 1440; `WindowPlacement.Place` puts the client area of a window as big
as the monitor at the monitor's top-left corner, which looks like borderless fullscreen with the title bar above the screen edge.

**The change** (as asked: the launcher's choice wins every time, the app stores the result):

* `AppArgs`: `--windowed` next to `--fullscreen`; the last one on the command line wins (`WindowModeChoice`: true / false / null).
* `GameLauncher.Plan(app, folder, paths, fullscreen, extra)`: every PLAY passes exactly one of `--fullscreen` / `--windowed`, from the switch (`LauncherModel.Play` passes `Fullscreen`).
* `StartupSettings.ApplyToConfig(config, langGiven, windowMode)`: the command line's window mode is **stored in the byte 0xA9** (the remembered state, committed at once when it changed, and
  at exit as before) and a pending `fullscreen=` line of the launcher is removed. **The file alone no longer decides anything**: a start with neither flag keeps the remembered byte,
  and a leftover line is ignored (it stays until a PLAY consumes it). `window`, `vsync`, `monitor`, `prompts` keys are untouched; `language` is still one-shot.
* The launcher's switch shows `fullscreen line (the pending choice) ?? the remembered byte`, and the byte's offset is one constant now (`AppSettings.WindowModeOffset`, used by the game,
  `StartupSettings`, `SaveTools`), so the switch reads the very value the game stores. After the game exits the launcher refreshes and shows what the game remembers (Alt+Enter in the game
  included).
* The game logs `window mode: windowed|fullscreen (command line, remembered)` or `(remembered)`.

Tests: `GameLauncherTests` (plan carries exactly one explicit flag, the list parses with the game's own `AppArgs`), `SettingsTests` (flags and last-wins, `--windowed` over a remembered fullscreen
and the reverse, no flag keeps the remembered byte and ignores a leftover line, a repeated mode needs no save but consumes the line, pending line then flag then the launcher reads the stored
byte through a real `SaveFile` round trip, every key still round-trips), `ExitFromTitleTests` (real app, hidden: `--fullscreen` stores 1 and consumes the line while `vsync=off` stays,
`--windowed` over it stores 0, a start with neither keeps 0 and leaves a stale `fullscreen=on` alone), the K17 launch test now passes `--fullscreen`.
`TsukiLauncher.exe --selftest` (temp profile) passes.

## 2. The title's logo and menu

The brief changed during the run (coordinator message): the user's observation is the PS4's **idle fade-out**: the logo and menu fade out by themselves after a minute or two without input and
any input brings them back; our port never faded them.

**(a) Start behaviour verified, left alone.** In the real app, hidden, with no input at all after boot: returning profile (boot notice, TM_CI intro, caution2, fade-in), a fresh profile after the
prologue (PRESS ANY KEY), languages en / ja / zt, real `PcInput` instead of the script, the hold mode (a temporary local switch, removed), the intro skipped by keys then nothing, and after
CONFIG / LOAD GAME / GALLERY with no key after the Esc: the logo and the menu came up by themselves every time (`scratch/K18/r1`, `r2`, `r3`, `r4`, `r5_*`, `r6`, `r9`, `r10`: pictures 3 s,
6 s and 10 s after the title was up were read). I did not find a stuck state, so the `covered` rule of `StepFx` and `UiBackdrop` are as K14 left them. (The one K18 exception: the quit
question over the title does not count as a screen covering it, so the logo stays while it is open.) The regression tests with no input at all are in (below) and pass on K14's rule too.

**(b) The idle fade-out.** PS4 evidence (eboot, `tools/eboot/disasm.py`): the title update 0xB06B0 keeps a counter at data 0x1762204: at 0xB074D it is set to **0xE10 = 3600 frames (60 s)** whenever the
pad's button word (`[r15+0x10]`) has any bit of `0xF9FC`, and it is decremented once a frame (0xB0739); the only reader is the state at 0xB0BDB (the exit of the title, which picks return value 1 =
attract mode; `system_flow.md` 4.3 already says nothing reaches it). **The logo/menu fade itself is not in the code**, so there is no fade speed to copy. Used: idle time **60 s (3600 steps,
`TitleScreen.IdleFrames`)** from that counter, fade = the logo's own fall (`la -= 1/60` per step, the PS4's rate for a covered title; the menu follows the logo as always, the copyright and the
moving background stay), any input snaps the logo back to 1 as every menu input does on the PS4 (docs 4.5.1). It is not a 90 s guess: if the user's 1 to 2 minutes is right, change one constant.

Behaviour (`TitleScreen.ReclaimTitle`, the K14 wake path): the clock counts steps in which the title is the top screen, Idle, with the menu fully up (not in PRESS ANY BUTTON), and no input; a pointer
move, click, wheel, key, direction or pad button sets it to 0 and, if the logo had faded out, shows logo and menu at once. **The press that wakes a hidden menu only wakes it** (Enter / click /
Esc do not also choose the item or ask the quit question; moves and directions still move the cursor): choosing an item that cannot be seen would be a trap, and the PS4 text does not say.
A screen or dialog on top, a story starting, or the fade-in restart the count.

Tests (`TitleTests`, `TitleKeysAppTests`): no input for the idle time -> hidden (shown 5 s and a few steps before, falling after, gone after 1.3 s, copyright and background still drawn, stays gone);
pointer move, click, wheel, direction and pad button each show them again at once and restart the clock (and it runs out again after the full time); input before the timeout, six rounds
(three idle times in all) -> never hidden; the waking Enter / Cancel is no answer; the clock does not run under the config screen; PRESS ANY BUTTON and the open quit question are never faded;
the same through `InputMapper` + `AppRuntime` with a real pointer sample. Plus the no-input tests of the first part (3.3 s / 6 s / 10 s after: new title with and without a save, boot notice + intro + title,
after CONFIG and LOAD GAME, after the gallery, three kinds of backdrop left up). Real app, `--fast`, keys then nothing, a pointer move: `scratch/K18/i1` (`contact.png`: shown, fading at the
idle time, hidden with only the background and the copyright, shown 10 steps after `move=`, shown again, hidden again 60 s later).

## 3. EXIT on the title

* `TitleItem.Exit` (7, a port addition) is the last entry, after GALLERY (5 or 6 items; the 6-row layout keeps the first row where it was and closes the pitch from 23.23 to 21.2 units so that
  EXIT stays above the copyright: letters end at y 1022, the copyright starts at 1032).
* **Art.** The five items are pictures in TITLE_PARTS child 0 (296 x 72 cells, identical in all languages: the items are English everywhere on the PS4 and so is EXIT); there is no X in them, so EXIT is
  drawn with the game's glyph font (`UiText.DrawGlowLabel`, the current language's pages). Measured on the sheet (alpha > 200): capitals 19 px high at rows 28..46 of the cell, 11 to 12 px between
  letters, white with a light-blue glow (192, 238, 254), cursor column cyan (17, 222, 248) with a faint cyan glow. Measured on the render: EXIT is 19 px high at rows 28..46 of its slot, gaps 12 px,
  centred at 963.5 (the cell's centre 964), en / ja / zc / zt (zc and zt need scale 0.395: their Latin glyphs are wider). Colour: white / cyan, glow: 25 copies of the glyph at three rings
  (the pages' dilated outline copy leaves a faint box). The look is the game's sans (en) or serif-like (ja, zc, zt) face, not the baked serif of the others: the letters are heavier than the thin art.
  Pictures read: `scratch/K18/ui_en|ui_ja|ui_zc|ui_zt/ui_title_*.png` (`ui-shot title`), real app with the cursor on EXIT `scratch/K18/x3_en/exit_cursor.png`, `x3_ja/...` (crops `crop.png`).
* **Selecting.** Enter, a click on the item (hit rect as the neighbours'), decide on a pad, or **Esc / right click / pad cancel anywhere on the title** (also over PRESS ANY BUTTON, where every other
  button still goes on; not while the menu is not up or a story is starting) open the PS4's own quit question: **ui_text 236 "Are you sure you want to quit without saving?"** (ja: セーブせずに終了して
  よろしいですか？), dialog 14 of the confirm table, the existing `ConfirmDialog`, cursor on No. Yes calls `IGameServices.RequestQuit()` (default no-op; `AppServices.QuitRequested`;
  `AppRuntime.ExitRequested`), and `GameApp.Loop` leaves its loop exactly like the window's close button (`running = false`, then the normal tail: save commit, summary, exit code 0).
  There is no "Quit the game?" string in the PS4 data; 236 is the only quit text.
* W / S / arrows / the pad's d-pad reach it (wrap: Up from the first item is EXIT, Down from EXIT the first), the pointer hovers and clicks it.

Tests: the K14 title tests now list EXIT (cursor wrap, WASD, gallery / config routes, pointer hit rects, `GalleryScreenTests`, `GalleryRealDataTests`), new: last item with and without CONTINUE, slot inside the
screen and above the copyright, glyph quads inside the slot and the five others as sheet cells, cursor colour (white / cyan), the dialog text id and cursor on No, Yes -> `quit` once, No and Cancel
return with the logo up behind the dialog, Esc / right click / pad cancel from any item, Cancel over PRESS ANY BUTTON, click on EXIT and a click under it, Cancel ignored while fading in and

## 6. Open issues

1. The visible window was never opened (rule), so fullscreen itself, the pointer path from SDL and the real mouse were not tried; the window-mode byte, the arguments and the settings are tested and the
   hidden app logs the decision. If the user still sees fullscreen with the switch off, look at `window mode:` in `last_run.log` and at the window-size preset (section 1).
2. The idle fade-out time is the PS4's 60 s counter and the fade rate is the logo's own; the PS4 code has no fade for it (section 2). The "stuck title" the first brief described was not reproduced
   (section 2a); the logo and menu come up by themselves in every route tried.
3. EXIT is drawn with the game's glyph font, not the baked serif of the neighbours (no X exists in the art); the cursor glow of the neighbours' third sheet column is not used by the game and not copied.
4. The launcher's switch shows the pending line while a PLAY has not consumed it; a direct start of `Tsuki.App.exe` ignores that line by design.
