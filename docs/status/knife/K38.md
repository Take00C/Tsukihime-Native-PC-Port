# K38: issue #7, "flowchart scene, Esc, flowchart again: crash, black / stuck"

Package K38 (label `k38`), run on 2026-11-01 on top of commit cccace4 (v0.1.2). A first attempt ran out of usage mid-task; this run read its diff and its
scratch runs, kept what was right, corrected what was not (section 4) and finished the work. Nothing is committed. Builds in `artifacts/k38` (`-warnaserror`,
0 warnings); the unchanged v0.1.2 code was built from a detached worktree of HEAD (`scratch/k38/wt_head`) into `artifacts/k38head` for the before / after
comparison. Every game run hidden and muted (`--hidden --mute --fast`, `SDL_AUDIO_DRIVER=dummy`, BelowNormal priority) on a fresh copy of a seed profile under
`scratch/k38/<run>/profile` (`scratch/k38/run2.sh`); the game folder, `%APPDATA%\Tsuki`, `%APPDATA%\shadPS4`, `artifacts/play*`, `artifacts/dist*` and the
public / release / upload folders were not touched.

The player's report (GitHub issue #7, v0.1.1 / v0.1.2): "If you enter a flowchart scene and then press escape and flowchart again, game crashes and it becomes
just black/stuck. ... tried it 3 different times and it happened all 3."

## 1. Root cause

It is not an exception and not a hang: the game keeps running with **no story and no screen**, so it draws black and nothing takes a key.

A scene entered from the gallery's flowchart is a replay (scene 3000 `ARCHIVE`, F024 = 1). During such a replay the system menu's FlowChart tab asks
"Do you want to return to the flowchart?" (dialog 12; knife `Confirm::EndReplay`). Its Yes called `IGameServices.EndReplay()` **at once, inside the dialog's
callback**, while the system menu and the dialog were still on the screen stack. `AppServices.EndReplay` set `StoryActive = false`, stopped the story's sound and
called `UiRoot.ReturnToGallery()`, which refuses while any screen is open (it pushes the title and the gallery over an empty stack only). So:

1. the story was gone, the gallery was never opened, and the system menu stayed up over black (the frozen scene is drawn only while a story runs);
2. the player's next Esc (or right click) closed the menu: an empty stack and no story. From then on every key went nowhere (the story input is routed only
   while a story runs, the menus only while a screen is open): a black window that takes no key until it is closed.

The PS4 / knife order is the other way round: Yes runs `leave_to_title` (sub_4CCA0 with byte_B359DC = 1, F024 kept): the menu and its backdrop fade out at
1/30 a frame, and only when they are gone does the story end; with F024 set it ends back in the gallery, which reopens on the chart (sub_4D7E0, knife
`end_story` -> `Action::GalleryBack`).

The in-game route (story -> Esc -> FlowChart -> a node -> "rewind to this scene?" -> Yes -> Esc -> FlowChart again) has no crash or black screen in v0.1.2
(section 3, run `head_s_en`; and 98 nodes in the real-data sweep on HEAD). It had one visible defect on the same path: after the jump (and after a load from
the menu) the menu's backdrop was left at full alpha, so the next system menu showed it at once instead of fading it in (`Backdrop.Fade(0)` "cuts to where it
was heading", which was full alpha, and `UiRoot.Clear` told the menu it was closed while it was still on the stack).

## 2. The fix

| file | change |
|---|---|
| `src/Tsuki.Ui/Screens/SystemMenuScreen.cs` | the dialog's Yes now leaves the way the Title tab does (`Leave(Leaving.Gallery)`): the menu and its backdrop fade out (1/30 a frame), the menu takes no input meanwhile, and once it is gone it clears the stack and only then calls `EndReplay()`. `_toTitle` became `Leaving { No, Title, Gallery }`; `LeavingStory` tells the tests. `OnClosed` resets the backdrop when it was the last screen (any way it went: its own fade, a hand-off, a load, a flowchart jump) |
| `src/Tsuki.App/Services/AppServices.Story.cs` | `EndReplay` ends the story (commit, outputs stopped as at a story's end) and leaves a pending gallery return (`TakePendingGalleryReturn`), the way `ReturnToTitle` leaves a pending title, instead of calling `ReturnToGallery` itself |
| `src/Tsuki.App/Play/AppRuntime.cs` | `ApplyPendingHandOff` (title or gallery, once no screen is open) runs before the menus step (as before) and again right after them and at the end of the step, so the title or the gallery takes over **in the same frame** the menu cleared the stack (the title hand-off used to leave one black frame). Last resort at the end of every step: no story and no screen -> the title, with the log line `nothing on screen (no story, no menu): back to the title` (never fired in any run of this package) |
| `src/Tsuki.Ui/Framework/UiRoot.cs` | `Clear` empties the stack first and tells the screens afterwards (top first), as `Step` does for one screen: an `OnClosed` sees the root as it is. Before, a screen whose `OnClosed` calls `Clear` (the gallery's replay hand-off, the backlog jump) under another such screen recursed until the process died of a stack overflow (shown by a test, section 5); and the gallery cleared with the title called the title's `ReturnFromGallery` on a title that was being removed |
| `src/Tsuki.Ui/Services/IGalleryServices.cs` | `EndReplay` documents its contract (called once the menu has faded out and the stack is empty) |
| `src/Tsuki.App/Play/GameApp.cs`, `src/Tsuki.Platform/GameWindow.cs` | an exception that ends the run hides the game window before the error box (`GameWindow.Hide`, `HideWindowForError`): a borderless fullscreen window that has stopped presenting would stand in front of an ownerless box, and the player would see a black screen that takes no key instead of the message. Verification verb `fault` (section 5) |
| `src/Tsuki.App/Play/InputScript.cs` | the `fault` verb (a screen whose step throws) |

The FlowChart tab of the in-game chart, `FlowchartChart`, `GameHost.FlowJump`, the restore, the movie / BGM restart and the blur were read and exercised
(the sweep of section 3) and needed no change.
