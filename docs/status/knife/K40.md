## 2. How it works (src/Tsuki.Launcher)

| step | code | rule |
|---|---|---|
| source | `Core/UpdateSource.cs` | `UpdateSource.DefaultRepository = "Take00C/Tsukihime-Native-PC-Port"` (the one line a fork changes); GET `https://api.github.com/repos/<repo>/releases?per_page=20` (not `/releases/latest`: our releases are pre-releases); `HostPolicy.GitHub` allows HTTPS on the default port to `github.com`, `api.github.com` and `*.githubusercontent.com` only, no user info; `HostPolicy.Loopback` (tests, `--update-api`) allows the loopback address only |
| client | `Core/UpdateClient.cs` | `SocketsHttpHandler` without automatic redirects: up to 5 redirects followed by hand, each checked by the policy (GitHub's `releases/download/...` answers 302 to `release-assets.githubusercontent.com`); headers `User-Agent: TsukihimeLauncher/0.1.3 (+https://github.com/<repo>)`, `Accept: application/vnd.github+json`, `X-GitHub-Api-Version: 2022-11-28`, no authorisation; 15 s for the list and the first byte of a download, 30 s stall limit per read; list at most 8 MB, SHA256SUMS.txt at most 64 KB, the zip at most its reported size (and 2 GiB); a partial file is deleted; network trouble is an error text, never an exception, for the check |
| choice | `Core/ReleaseVersion.cs`, `Core/UpdateFeed.cs` | tags `vX.Y.Z` / `X.Y.Z` only (a suffix such as `-rc1` is skipped); drafts skipped, pre-releases taken; the asset `Tsukihime-vX.Y.Z-win-x64.zip` (exact name) **and** `SHA256SUMS.txt` must be attached and in state `uploaded`; the highest version greater than the running one wins; the running version is the launcher assembly's informational version without `+commit` and `-personal`. Notes: Markdown marks removed (headings, emphasis, code ticks, link targets, the common HTML tags, comments, rules), list items as "•", 20,000 characters at most |
| personal build | `Core/Updater.cs` `LauncherBuild` | the `TsukiPersonalBuild` metadata, a `-personal` version or `PERSONAL_BUILD.txt` beside the launcher (package K28's marks): no check, no update, the Help page says so |
| prepare | `Core/Updater.cs` `PrepareAsync` | the staging folder `update-staging\` inside the launcher's folder is emptied; SHA256SUMS.txt first (it must list the zip, else refused before the zip is fetched); the zip with progress and Cancel; its SHA-256 must be the listed one (`Core/ReleaseSums.cs`: `<hex>  <name>` or `<hex> *<name>`); any failure removes the staging folder. Before it: the game of this folder must not run (`GameLauncher.IsGameRunningFrom`: a Tsukihime.exe process whose image is this folder's; another copy of the port does not count), the folder must be writable (`UpdateInstaller.ProbeWritable`), the drive must have 4 x the zip free, and the .old files of an earlier update must be gone |
| unpack and check | `Core/UpdateInstaller.cs` `Extract`, `Check` | every entry checked: no `..`, empty or `.` part, no rooted path or drive letter, no `:` (alternate streams), no name ending in a dot or space, no device name, both slash kinds; the target must be inside the folder; duplicates (case-insensitive), more than 20,000 entries or 4 GiB refuse the whole zip, an entry longer than it says too; then `TsukihimeLauncher.exe` and `Tsukihime.exe` at the top (one wrapping folder tolerated), no `PERSONAL_BUILD.txt` anywhere, `TsukihimeLauncher.dll` readable with no personal mark and **its version equal to the tag's** (else the update would offer itself again after the restart) |
| apply | `UpdateInstaller.Apply` | every step written to `update-staging\journal.txt` before it is taken; each file that exists is renamed to `<name>.old` (Windows allows renaming a running program and its loaded libraries), then the new one is moved in; `TsukihimeLauncher.exe` goes last; on any failure every step taken is undone in reverse and the journal ends "rolled back"; files the release does not have are left alone; nothing outside the folder (the target must be inside it and not in the staging folder) |
| restart | `LauncherApp.xaml.cs` `RestartInto`, `AfterUpdate` | the old launcher releases its single-instance mutex, starts the new `TsukihimeLauncher.exe` with its own arguments plus `--after-update <pid> --updated-from <version>`, and exits; the new one waits for that process (30 s at most), deletes the `.old` files its journal names (retrying while they are in use) and the staging folder, and says *Updated from ...*. At every start a left-over staging folder is cleaned the same way; a journal without its end (power loss before the launcher was moved) is rolled back first; files still in use keep the journal for the next start |
| settings | `src/Tsuki.App/Services/AppSettings.cs` | `update_check=on|off` (`AppSettingsData.UpdateCheck`), so the game keeps the key when it rewrites settings.ini |

Never touched by an update: `%APPDATA%\Tsuki` (saves, settings, backups, icons; only `launcher.log` is appended), the game folder. The check never blocks the
window (async; the window does not wait for it).

## 3. Release side

missing at the top, `PERSONAL_BUILD.txt`, an escaping entry, a `TsukihimeLauncher.dll` whose version is not the name's (it says which `<Version>` to set).

line, the layout) say that every release attaches the zip **and** `SHA256SUMS.txt`, with the exact names; `docs/SETUP_GUIDE.md` / `.txt` got section 4.7.

## 6. Open issues

1. **Not tried against the real GitHub** (the rule: no network calls in tests). The API answer, the asset fields (`name`, `browser_download_url`, `size`,
   `state`), the 302 from `github.com/.../releases/download/...` to `release-assets.githubusercontent.com` (older uploads: `objects.githubusercontent.com`)
   and the pre-release / draft flags were built from GitHub's documented behaviour and served by the loopback stand-in. The first real proof is the user's
   plan: publish v0.1.3, then v0.1.4 with both files, and press the button in a v0.1.3 folder.
2. The visible window was not opened (offscreen renders and the verification modes only): the button's hover glow, the overlay's keyboard focus, the window
   closing during a download and the restart of a *visible* launcher (the same `RestartInto` path the self-test's restart mirrors, with the window mode's
   arguments) are code-checked, not clicked.
3. A folder under Program Files was only probed (`ProbeWritable` against the real `C:\Program Files` as a non-elevated test, nothing created); the overlay's
   message for it is rendered (`update_not_writable.png`). An elevated launcher could write there and would update normally.
4. Files of the old version that the new release no longer has are left in the folder (harmless: the deps.json files decide what loads). A release that
   removes a file therefore leaves the old copy behind; a full reinstall clears it.
5. Players on v0.1.0..v0.1.2 have no button: they must fetch v0.1.3 (or newer) by hand once (README step 4, PUBLISHING section 8).
6. GitHub allows 60 unauthenticated API calls per hour per address; one start is one call. A 403/429 with `x-ratelimit-remaining: 0` is logged as "GitHub's limit
   of checks per hour was reached" and the start goes on quietly.
