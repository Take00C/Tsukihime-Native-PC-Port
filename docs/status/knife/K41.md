Package K41 (label `k41`), run on 2026-11-01 in the git worktree `scratch/wt_v013` (branch `v0.1.3-updater`, K40's commit `04c73b4` on `cccace4` = v0.1.2).
The review's changes are a second commit on the branch, with the same message ("v0.1.3: launcher update button (issue #6)", the one this workflow
allows; not pushed), on top of `04c73b4`; the builds and publishes below were made from the working tree before that commit and carry `+04c73b4...` in
their version.

## 1. Bugs found and fixed

| # | where | the bug | the fix | the test (red on K40's code, green now) |
|---|---|---|---|---|
| 1 | `UpdateInstaller.RepairInterrupted` | a journal line `new <file>` whose `old <file>` line had no `.old` copy left was treated as a file **new to the folder and deleted**. After a "rollback incomplete" (or a repair that put back some files and not others, retried 5 s later or at the next start) that file is the **restored old version**: the repair deleted it (here `Tsukihime.exe`, so the game was gone) | a file the journal names as replaced is never removed as new | `UpdateInstallerTests.AnIncompleteRollbackIsFinishedAtTheNextStartAndKeepsTheFilesItHadPutBack` (K40's code: `FileNotFoundException ... Tsukihime\Tsukihime.exe`) |
| 2 | `UpdateInstaller.Cleanup` | when the repair could not put a file back (it was in use), the cleanup went on to **delete the `.old` copies**, the only old version of those files; the next start then had nothing to put back (and, with bug 1, deleted the file itself) | a repair that cannot finish returns at once: nothing deleted, the journal kept for the next start | `UpdateInstallerTests.ARepairThatCannotFinishKeepsTheOldCopiesForTheNextStart` (K40's code: `FileNotFoundException ... | 3 | `UpdateInstaller.RepairInterrupted` | the repair renamed and deleted the files its journal names **anywhere** (the deletion loop already kept to the folder): a folder copied with its `update-staging` folder repaired the original folder's files | `IsInside`: only paths inside the launcher's folder and outside `update-staging\` are touched, in the repair and in the deletion loop | `UpdateInstallerTests.TheRepairOfAnInterruptedJournalNeverTouchesFilesOutsideTheFolder` (K40's code: the other folder's file was replaced by its .old) |
| 4 | `UpdateFeed.Read` / `LauncherModel.OpenReleasePageCommand` | the release's `html_url` from the answer went **unchecked to `Process.Start(UseShellExecute = true)`** ("Open the release page"): a `file:///...exe`, `C:\...exe`, UNC or other-scheme address would start a program, the one path where something from the answer ran without any checksum | `UpdateFeed.ReleasePage`: kept only when `https`, default port, no user info, host `github.com`; else null, and the button opens the repository's Releases page (a constant) | `UpdateFeedTests.AReleasePageThatIsNotAGitHubPageIsNeverOpened` (9 cases: file URL, drive path, UNC, http, `github.com.evil.example`, user info, port 8443, `ms-settings:`, not a URL; 9 red before), `TheReleasePageOnGitHubIsKept` |

Bugs 1 to 3 need a file that cannot be renamed or deleted while the update or the repair runs (a virus scanner, the game of the folder started in the
second of the swap, an indexer), or a copied folder; they never show in the normal path, which K40's tests cover. Bug 4 needs a forged API answer (TLS to
api.github.com prevents it); it is defence in depth on the one place a URL from the answer reaches the shell.

A test-harness race, found when the Synthetic suite ran in Release: `UpdateClientTests.CancelStopsTheDownloadAndRemovesThePartialFile` failed once in its
`Dispose` (`IOException: The process cannot access the file 'big.bin'`), because `FakeGitHub.Dispose` waited for its accept loop but not for an answer
still being sent (the cancelled 64 MB file, held open by the server task) before the test deleted its folder. The product code was right (the test body
passed). `FakeGitHub` now keeps its answer tasks and `Dispose` waits for them (10 s at most); the client tests then passed 5 runs out of 5 in Release
(`client_loop_1..5.log`) and the full suite in both configurations.

## 5. Open issues (not fixed here)

1. **No automatic way back after the restart.** Once the new launcher has been started there is no check that it runs: a release that crashes at start
   (not self-contained, a file missing) leaves the folder on the new files, and the player must download a good zip by hand. A fix would have the old
   launcher wait for the new one to take the single-instance mutex and roll the journal back (it still has every `.old` file) when the new process ends
   first; that changes the restart protocol and was left for a package of its own. `docs/PUBLISHING.md` section 8 now says to run `release-check` and to
   update a copy of the previous release's folder right after publishing, and to take the zip off the release at once if the new launcher does not start.
2. **The restart contract** (`--after-update PID --updated-from X.Y.Z` and the journal format) must stay accepted by every later launcher, or the
   restart ends in the usage message (exit 64); written into `docs/PUBLISHING.md` section 8.
3. `SHA256SUMS.txt` comes from the same release as the zip: it catches a damaged or cut-off download, not someone who controls the repository's releases
   (there is no signature). `*.githubusercontent.com` also admits `raw.` and `gist.`, and the asset URL is not tied to the repository's path; both only
   matter with a forged API answer.
4. Closing the window during "Replacing the files..." (well under a second) ends the process in the middle of `Apply`; the journal repair at the next start
   handles that now (bugs 1 to 3), but the window could refuse to close in that second. A power cut between renaming `TsukihimeLauncher.exe` to `.old` and
   moving the new one in leaves no launcher to run the repair (milliseconds; the game itself is already the new version then).
5. A running version with a suffix (`0.1.4-rc1`) reads as 0.1.4, so v0.1.4 would not be offered to it; the port builds no such versions.
6. As K40: not tried against the real GitHub (the rule), the visible window not opened (the restart of a visible launcher is code-read only).

## 6. For the release plan (v0.1.3, then the crash fix as v0.1.4)

This branch is v0.1.3 (`<Version>0.1.3</Version>` in both projects). The crash fix becomes v0.1.4 only if its branch **contains this branch** (K40 and K41)
and sets `<Version>0.1.4</Version>` in `src/Tsuki.App/Tsuki.App.csproj` and `src/Tsuki.Launcher/Tsuki.Launcher.csproj`; its release must be tagged
`v0.1.4`, not a draft, with `Tsukihime-v0.1.4-win-x64.zip` and the `SHA256SUMS.txt` that `release-sums` writes for it (section 4 shows exactly that
pair updating a v0.1.3 publish of this branch over the loopback stand-in).
