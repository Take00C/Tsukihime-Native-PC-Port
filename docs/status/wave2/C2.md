**New engine fact (measured).** I checked under unicorn on the eboot's own handlers what happens after a jump. The
script `tests/Tsuki.Tests.Data/Flow/jump_exits_emu.py` stubs the label lookup with a target and lets ScriptStep run on. The result:

| statement | after the label lookup |
|---|---|
| `_IF__` (condition false) | ScriptStep **returns** with the cursor at the label |
| `_GOTO` | ScriptStep **returns** with the cursor at the label |
| `_GOTS` | **continues** at the label in the same call (the target's `_WKST(F7,eq,99)` ran) |
| `_IFNX` with a label | **continues** at the label in the same call |
| `_IFNX` without a label, and a true `_IF__` | continue with the next statement |

`ScriptVm` follows this table. script.md 3.6 only said "may yield".

## Decisions and deviations

- **The trace runs on the statement's own bytes.** The VM passes the segment (statement) bytes to `VarCommands`, as the
  oracle tracer does with `raw_bytes`; the fuzz passes `text + "_DMMY();"` as `compare_one` does. Reads past the span end
  are 0 and copy loops stop there, as in `tsuki.vm_vars`.
- **Default policy.** `OutOfBlockPolicy.Reject` is the default, following RUNTIME_REQUIREMENTS item 6 ("port: reject
  out-of-range"). The retail traces stay inside the block.
- **SEL\* handling.** The VM runs the variable side of `_SEL*`, then calls the host for the UI; SELD / SELA / SELS still
  yield as in the engine.
- **Interpreted from docs, not emulated by me:**
  - **`ZY` copy.** It copies from name + 8 up to `)` `,` `;`. script.md 3.7 gives the start but not the end [E start,
    H end].
  - **Label match.** The record name is taken up to its first byte <= 0x20 and must equal the cut wanted name
    (script.md 2.4).
  - **Missing label.** It throws `ScriptFlowException`; in the engine it reads garbage.
- **Marker table bounds.** Blocks outside 0..0xFB3 are never written to readmax and read as 0. The engine bound is
  signed-upper only and reads the memory next to the table.
- **Truncated segments.** A truncated segment (no `;` within 0x300) throws in TSUKI_DEV builds; Release cuts it as the
  engine does.
