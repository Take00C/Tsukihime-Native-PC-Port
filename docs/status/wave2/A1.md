# A1: MZP images (PACE 7.2 #2), status

Written 2026-10-25 by the A1 agent. Package: port `tools/tsuki/image.py` (+ `mzp.py`, already ported by the data stream) to
`Tsuki.Data.Images`, SIMD for RGB565+LO+A, the stratified picture-SHA-1 exporter through the oracle runner, the all-pictures run in
`Tsuki.Cli decode-all`, and the data stream's Python generators moved to `tools/oracle/data.py` (decision 2). Every number below comes
from a run on this machine (AMD Ryzen 7 5800X3D, 8 cores / 16 threads, 64 GB; Windows 11; .NET 10.0.402; Python 3.11.9 with numba).
Numbers, commands and identifiers only.

## Timings (decision 4: each timed run held `artifacts/gpu.lock`; warm file cache; machine otherwise at 2-10 % CPU before and after)

| run | wall | what |
|---|---:|---|
| Python oracle, all pictures (`oracle.image`, 14 processes), two runs | **232.9 s** and 247.7 s (hashing; 237.6 s and 280.3 s with census, the 2,000-picture part and manifests) | 35,630 pictures, 493.8 GB of displayed RGBA hashed; the two `pictures.tsv` files are byte-identical |
| C# `decode-all --pictures --complete --expect`, Release, 16 threads, two runs | **115.4 s** and 119.2 s | the same pictures: 831,840 tiles decoded, 493.8 GB hashed, 4.14-4.28 GB/s, 1,036-1,070 Mpx/s; both `--picture-hashes` files are byte-identical to the oracle's `pictures.tsv` |
| Python oracle, 2,000 stratified pictures (14 processes) | 20.9 s and 24.0 s (26.5 s with census, entry hashes and manifest) | 29.6 GB of displayed RGBA |
| C# sweep of the same 2,000, 16 threads | 9.9 s Release, 11.0 s Debug | 29.6 GB hashed (`decode-all --pictures --expect samples/golden/image/sha1/pictures.tsv`) |

The C# run is about 2.0-2.1x faster than the Python run (16 threads against 14 processes). Hashing is the biggest single cost in the C# run: the streaming SHA-1 of IMG1481 takes
596 ms on one thread (decode + band copy + .NET `IncrementalHash` SHA-1) against 177 ms for the decode alone (rows below), so roughly two thirds of the per-picture time is hashing
and copying. It is a test and tool cost; the runtime hashes nothing.

Per-stage single-thread numbers (`decode-all --bench-pictures`, Release, best of 7, largest picture of each format):

| picture | stage | ms | Mpx/s |
|---|---|---:|---:|
| HEP8 IMG1481 (330 live tiles, 346 MB stored RGBA) | MZX0 only | 149.05 | 580 |
| | convert (palette gather) | 29.29 | 2,953 |
| | `ToPicture`, 1 thread / 16 threads | 177.25 / 22.23 | 488 / 3,892 |
| | stream SHA-1, 1 thread | 596.44 | 144 |
| RGB565+LO+A IMG1481_20_00 (345 live tiles, 362 MB) | MZX0 only | 272.27 | 332 |
| | **convert, scalar** | 126.29 | 716 |
| | **convert, Vector128** | 27.37 | 3,305 |
| | **convert, Vector256** | 18.79 | **4,813** |
| | `ToPicture`, 1 thread / 16 threads | 247.91 / 28.76 | 365 / 3,144 |
| PAL8 BLACK (20 live tiles) | `ToPicture`, 1 thread / 16 threads | 0.99 / 0.60 | 2,643 / 4,378 |

The SIMD conversion of RGB565+LO+A is **6.7x** the scalar loop (4,813 against 716 Mpx/s; S4 measured 494 Mpx/s for its scalar loop). With it the
conversion stage of the worst picture is 18.8 ms for 362 MB, below its MZX0 stage (272 ms), so MZX0 is again the cost of a decode, not the pixels.
`ToPicture` on 16 threads takes 22.2 ms (HEP8) and 28.8 ms (RGB565) for the two largest pictures, against S4's 25.8 / 46.9 ms with 16 workers.

## What was built

`src/Tsuki.Data/Images/` (namespace `Tsuki.Data.Images`; no P/Invoke, managed pointers and `Vector128/256` only):

| file | content |
|---|---|
| `ImageHeader.cs` | `PixelFormat` (PAL4, PAL8, HEP8, RGB565+LO+A), `ImageFormatException : ContainerFormatException`, `ImageHeader.Parse` (port of `parse_header`: zero dimensions, tile counts, exact length, the palette rule of VA 0xD8DC7, unsupported types; CSM1 unswizzle and alpha fix of the header palette; shown size with the border rule; tile origin and displayed window; flags) |
| `TileConverter.cs` | decompressed tile to RGBA8 for all four formats, strict HEP block check like `strict=True`, PAL4 as one linear nibble stream with index 0 for an odd last texel, HEP palette alpha `2*min(a, 0x7F)`, the **RGB565+LO+A converter in scalar, Vector128 and Vector256** (`SimdLevel`; 16 pixels per step: widen, shift and mask in u16 lanes, interleave with `WidenLower/Upper`) |
| `ImageMzp.cs` | an mrgd00 container as an image: `IsImage` (the rule of `sniff.classify_mzp`), `Open`, `DecodeTile` (MZX0 into a per-thread `TileScratch`, size checks, errors name the tile), `ToPicture` (the `Picture` of the data contract: stored tiles with border, flag-0 tiles empty, displayed window and position, optional parallel tile decode), `DecodeDisplayed`/`Assemble` (the bitmap of `decode_image`, for tests and tools only) |
| `PictureHasher.cs` | SHA-1 of the displayed picture without building it: one tile row at a time into a band buffer (25 MB for the widest picture instead of 343 MB), per-thread reusable buffers |
| `PictureWalker.cs` | finds the image MZPs in a container the way the oracle's census does, and the label scheme (`allpac3#5/17`) |
| `SpriteName.cs` | port of `split_sprite_name` / `SpriteName` (`IsBase`, `Group`) |

`src/Tsuki.Cli/Commands/`: `PictureSweep.cs` (the all-pictures run), `ImageBench.cs` (per-stage benchmark), options on `DecodeAllCommand.cs`:
`--pictures`, `--picture-hashes FILE` (TSV in the oracle's format), `--expect FILE`, `--complete`, `--bench-pictures`, `--reps N`; the existing stream mode is unchanged.

`tools/oracle/image.py`: area `image`, parts `sha1` (2,000 stratified pictures: strata = source x format x tile height x size class, anchors = the
largest, widest, tallest and smallest of every format, one of each header variant, the named pictures of images.md 10, every rare stratum of up to 20 taken whole,
the rest proportional with a seeded systematic draw) and `all` (every picture). Output `samples/golden/image/<part>/pictures.tsv` plus manifests with
hard checks (35,630 pictures, the four format counts, 2,000 selected, every format sampled).

`tools/oracle/data.py`: decision 2. The generators of `gen_golden_data.py` and `all_stream_hashes.py` moved here (`python -m oracle.data golden|hashes|run`);
`tests/Tsuki.Tests.Data/Oracle/gen_golden_data.py` and `all_stream_hashes.py` are 25-line thin callers. Proof that nothing changed: the module regenerated
`samples/golden_data` into a scratch folder with **23 of 23 files byte-identical** (only `bench/python.json`, which holds timings, differs); the thin callers
reproduce `archives.tsv` / `buildcheck.json`, and `hashes` + `decode-all --hashes` agree on 4,912 of 4,912 streams of `allpac4` + `parts`. It also has the oracle area
contract: `python -m oracle.data run` writes the same files to `samples/golden/data/` with a manifest, and `--verify` reports 0 problems.

## Open issues

1. **Register the new areas in `tools/oracle/run.py`** (not an A1 file): `AREAS` needs `"image": "oracle.image"` and `"data": "oracle.data"`, so that `python -m oracle.run image`
   and `--list` work. Until then `python -m oracle.image` and `python -m oracle.data run` add themselves to the runner's table and call `oracle.run.main`. The other
   wave-2 exporters (`script`, `textbox`, `audio`) have the same need; a discovery rule (every `oracle/*.py` with `AREA`) would end it.
2. **`GoldenData.Dir` still reads `samples/golden_data/`** (`tests/Tsuki.Tests.Data/GoldenData.cs`, not an A1 file). The same files, byte-identical, now also come from
   `python -m oracle.run data` into `samples/golden/data/` with a manifest. When the lead flips the default and the thin caller's `--out`, the legacy folder can go.
3. **`bench-image` could not be a command of its own**: registering it needs `src/Tsuki.Cli/CliApp.cs`. It is `decode-all --bench-pictures` for now.
4. `compose()` (the float "over" of sprite faces) and the catalog `render` of `image.py` are not ported here: the runtime composes layers on the GPU, and the catalog is A2's. `SpriteName` is.
5. The moved generator code in `oracle/data.py` is verbatim (so its output stays byte-identical) and is not mypy-clean (12 errors, untyped dicts); the new `image.py` is.
6. `ImageMzp.ToPicture` allocates one array per tile (1 MiB tiles go to the large object heap). The upload scheduler (D1, S4's rules 4 and 5) should call `DecodeTile` into its own pooled
   buffers; the API takes a caller-owned span for that.
7. The stratified sample is fixed (seed 20261026), not drawn anew per build; a second sample would need another seed in `oracle.image.SEED`.
8. Timings are with a warm file cache. A cold read of the 24 GB `allpac1.mrg` (about 3.7 GB/s on this NVMe, S4) adds a few seconds, not measured here.
9. `IGameData.Picture` is not implemented here: `GameFolderSource` is A3, which calls `ImageMzp.Open(...).ToPicture()`.
